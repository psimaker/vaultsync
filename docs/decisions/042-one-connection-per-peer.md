# 042 — One connection per peer, enforced: the multi-connection promotion race has no second connection to land on

**Context.** A server folder with a heavy deletion history crash-looped the app about one second after connect, at index exchange; a small control folder from the same server synced, and a server-side index rebuild made it go away (#135, #185). A loopback harness (a real peer built from the pinned tree, 7,500 tombstones) reproduced the signature on `main`: the bridge closed the connection with `handling index for <folder>: folder is not running`, and the folder never settled. Syncthing 2.x opens up to three connections per device; each side promotes the first connection *it* saw to carry index messages, the two sides can promote different connections, and an index arriving on the other one hits `handleIndex` without a registered index handler, which closes that connection. A heavy index keeps the exchange running long enough for a second connection to arrive mid-exchange, so it never completes.

**Decision.** Two layers. (1) The bridge pins every peer to a single connection (`numConnections = 1`, new devices in `AddDevice`, existing ones through an idempotent migration on start); Syncthing negotiates the count through the hello, so a peer that asks for three uses one with us. (2) Fork patch `004-enforce-negotiated-connection-count`: two simultaneous dials pass the accept check on both sides before either has counted the other, and upstream never closes the extra — the patch closes the newest connections beyond the negotiated count by connection ID, which starts with the sum of both hello timestamps and is therefore ordered identically on both ends, so both sides keep the same connection. The harness stays in the bridge suite and asserts the exchange settles, the connection holds, and the peer holds exactly one connection.

**Why.** With exactly one connection there is one candidate for promotion on both sides, so index messages cannot arrive on an unregistered connection; a phone gains nothing from parallel connections to one peer.

**Rejected alternatives.** Sorting the model's connection list by ID so both sides promote the same one: a stock peer keeps arrival order, so the sort creates disagreement where none existed. Tolerating an index on a non-promoted connection in `handleIndex`: changes protocol behaviour for every peer version with no upstream fix to align with.

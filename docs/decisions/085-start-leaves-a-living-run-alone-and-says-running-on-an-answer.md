# 085 — `vaultsync start` leaves a living run alone, and says "running" only on an answer

**Context.** `vaultsync start` on a Mac loaded the service's job afresh whenever launchd still had it: it enabled the job, booted it out, waited until it was gone and bootstrapped it again. That is what a stop that ran out of time needs (#175). It also met a run on its way up. On macOS 27.2 with a stalled download of the pin (#267's case), a second `start` ended the run and loaded a new one, and the download began again from its first byte. And on both systems start said "✓ VaultSync is running again." as soon as the service manager counted the run as running, which is from its first moment: on macOS 27.2 after 1 s and under systemd after 0.13 s, while no control socket existed yet (#290). launchd was measured on macOS 12.7.6 and 27.2. A job's own state in `launchctl print` is `running` only while its process lives. It is `spawn scheduled` between two spawns, `SIGTERMed` once it is booted out while its process has not ended yet, and the print fails once the job is gone. Whether a live run stays alive, `print` does not tell.

**Decision.**
1. **start leaves a living run alone.** On a Mac, after `launchctl enable`, start leaves the job as it is where all of these hold:
   - `print` shows the job's state as `running`;
   - the program launchd loaded is the one the LaunchAgent file names, or `print` names none;
   - the engine lock (`agent.lock`) is held.

   Every other state is loaded afresh as before: between two spawns, idle, on its way out, an older definition still loaded, the lock free, and a lock that cannot be looked at. On Linux nothing changes in what start sends: `systemctl --user enable --now` leaves an active unit alone by itself (seen with a run on its way up). One look at `systemctl --user is-active` before it tells whether the unit was already active.
2. **A run takes the engine lock before its install,** before anything slow such as a pin's download, and every park comes before it. Both are now load-bearing for start too. The lock tells a run on its way up or syncing from one that parks, one just spawned, or one that has given up. So do two more steps of `run`: a run refused at the lock holds nothing afterwards, and the control socket is served only under the lock. Tests that drive the real `run` pin all four (`TestIssue290_EveryParkComesBeforeTheEngineLock`, `…HoldsTheEngineLockWhileItsPinDownloads`, `…RefusedAtTheEngineLockHoldsNothing`, `…TheSocketIsServedOnlyUnderTheEngineLock`). A later change that moves the lock after the install, or a park after the lock, changes this rule with it.
3. **"running" only on an answer.** After the start, on both systems, start waits for the agent to answer on its control socket, read afresh from `agent.json` at each look: 40 looks a quarter second apart (about 10 s), each ask with 10 s. An ask that gets no answer in its time ends the wait, as in the menu-bar app since #288, so one wait lasts at most about 20 s: 39 quick misses, then one silent ask. It asks for a path no agent serves (`/v1/`), so the agent's own HTTP server answers, with a 404, without a word to the engine. Any answer counts, an error included; what it says about syncing is `vaultsync status`'s to tell. `/v1/status` asks the engine first: on a macOS 27.2 VM with two cores it took up to 8 s right after a start, where the 404 took at most 1.3 s. Beside a desktop-v0.2.0 service whose socket was there, start got no answer to `/v1/status` within the 10 s. On an answer start says "running again", or "already running" where it left the run alone (on Linux: where the unit was already active). Without one it refuses nothing:
   - It says that the service runs but does not answer yet, that it may still be installing its sync engine, that `vaultsync status` says where it stands, and that `vaultsync stop`, then `vaultsync start`, ends it if it stays so. `stop` ends a run that ignores TERM too: launchd ends it about 5 s after `bootout` (measured).
   - Where the run recorded that it could not open its control socket (`control-socket-error.txt`), it syncs on without one, and a stop and start would only make the same socket fail again. start says that instead, names the file, and says that `vaultsync status` asks the engine directly. The file goes once a run serves its socket, and with a clean stop.
   - Beside a service of another build, start keeps its line that leaves syncing to `vaultsync status`, and says when that service does not answer yet.
4. **The guard.** launchd's states were measured on macOS 12.7.6 and 27.2 only. A version in between could show `running` for a job that a stop which ran out of time is still removing. Then start would leave it alone, get no answer, and the service would stay down until the next login: #175's failure, which loading every job afresh used to rule out. So where start left a job alone and got no answer, it looks at launchd once more. Where the job is gone, between two spawns or on its way out, it loads it afresh as in point 1 and waits for an answer once more. It is one look, and one more bounded wait, only on that path (`TestIssue290_ALivingRunThatIsGoneByTheEndOfTheWaitIsLoadedAfresh`).

**The look at the lock and an older run.** `lock.Probe` holds the lock for an instant (`flock` exclusive and non-blocking, then let go). A run of this build that takes the lock in that instant waits `engineLockGrace` (decision 079) and takes it. desktop-v0.2.0 and desktop-v0.3.0 take the engine lock once, with no grace, before their install; desktop-v0.1.0 takes it after its install. This was read from their tags, not measured. Such an older run that meets the look in that instant refuses as "already running" and exits. But then the look itself held the lock, so it found it free, and start loads that very job afresh, as it did every running job before. The run that failed is the one start replaces at once. A bootstrap starts the job without launchd's 10 s throttle: measured on macOS 27.2, a bootstrap 5 s after the previous spawn spawned within the second. The trace is one line in the older run's log. The look is made only on a Mac, and only for a job whose state is `running`. The instant itself was not measured: it lies between the older run's spawn and its lock, and no rig hits it on purpose.

**Why.**
- A run on its way up loses its progress to a restart, and gains nothing from it. A pin's download began again from zero.
- The engine lock is the one mark a run of VaultSync's makes before anything slow. launchd cannot tell a parked run from a syncing one: both are `running` with a stable pid.
- The service manager's "running" says a process exists, not that VaultSync came up. Only the agent's answer says that, and a run that ends before its socket never gives one.

**Rejected alternatives.**
- *Leaving every `running` job alone.* A run that parks, or a definition launchd loaded before a setup that could not reload it, would then stay as it is. The lock and the loaded program tell these apart.
- *A look at the lock that takes nothing.* `fcntl(F_GETLK)` is not documented to see `flock` locks on macOS; `lsof` is slow and its output would be parsed; `/proc/locks` is Linux-only, and Linux needs no look.
- *Looking only where the service runs this very build.* That narrows the instant without removing it, and ties the rule to the comparison of programs on disk, which #416 reworks.
- *A "starting" mark in `agent.json`.* It moves the format that released builds read, and the lock says the same.
- *Asking `/v1/status` for the answer,* as the menu-bar app does. It waits on the engine, which is slow right after a start, and start would call an agent that has come up one that does not answer. A new `/v1/ping` would answer the same as the 404 does, and agents from desktop-v0.2.0 on would answer it with that 404 anyway.
- *Refusing where no agent answers.* A run on its way up is no failure, and the menu-bar app would notify on every slow start.

**Not covered.**
- A service on an older build still loads a living run afresh when its own `vaultsync start` runs. This decision holds from the release that carries it.
- A run that holds the lock and never answers is left alone. start says so and names `vaultsync stop`, then `vaultsync start`.
- A `vaultsync run` in a terminal that holds the lock while the service's job happens to show `running` is taken for the service's run.
- So is `setup --no-service`, which runs its temporary engine under the engine lock. A service whose job shows `running` in the instant before its run refuses as "already running" is left alone, and start says it does not answer yet. Before, start loaded it afresh, and the new run met the same lock and refused too. Only the words differ, and "running again" was the less true of the two.
- VaultSync's own copy replaced outside setup, for example by hand, leaves its old process running: no watch ends it, as one ends a replaced VaultSync for Mac. start then leaves that run alone and says "already running". Which build a running service runs is #416's question.
- Overlapping starts (#290's third point).

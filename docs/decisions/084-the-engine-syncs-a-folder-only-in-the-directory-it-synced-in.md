# 084 — The engine syncs a folder only in the directory it synced in

**Context.** Decision 063 records which directory a folder synced in — the file number of its marker, with the folder's index ID and an anchor — and asks the record where the bridge re-points a folder whose directory is gone. A copy put in the folder's own place needs no re-point (#329): in the Files app the vault's folder is deleted and an earlier duplicate is renamed to its name. The path is alive and holds a `.stfolder`, so the engine's `CheckPath` passed, and the folder's next scan took every difference for a change made on this iPhone: what the copy lacks went out as deletions, its older notes as the current versions, to every device. `TestIssue329_ACopyInTheVaultsOwnPlaceKeepsThePeerWhole` showed it against a real peer for a copy put in place while VaultSync is closed, `TestIssue329_ACopyPutInPlaceWhileTheEngineRunsKeepsThePeerWhole` while the engine runs, where the watcher's scan sent the copy out ten seconds after it was put in place. The record did not even keep what it knew: the path reconcile noted every live folder's marker, so the first reconcile after a start wrote the copy's number over the vault's.

**Decision.** (1) The record also holds the file number of the directory that holds the marker — `.stfolder` — read with the marker's through one open handle of that directory: the marker's number is always one read inside the directory whose number comes with it. (2) Whenever the engine's `CheckPath` has found a folder's directory and its marker entry — before every scan, every pull and every commit of scan results, and before every write of the folder's filters (069) — it asks whether the `.stfolder` at the folder's path is the one the record names (fork patch 007: a check the bridge installs before the engine starts and removes once it has stopped). A record that applies — same anchor, same index ID — and carries that number: the same `.stfolder` passes, whatever its marker file is now, made anew or gone; another `.stfolder`, or a link or a file in its place, is refused with "folder directory is not the directory this folder synced in", which the app shows as a copy in the vault's place. A copy carries a `.stfolder` of its own, so a marker whose number was carried into it changes nothing here — in this check; the repair still asks the marker alone (Not covered). A record that waits for `.stfolder`'s number (see "The update") holds the folder to its marker: the recorded marker at the path passes, anything else there is refused. No record, one that does not apply, or one written by 3.0.x: the folder goes on as before. `.stfolder` is opened without following a link in its place: the engine makes it as a directory and never syncs it, so no peer can put a link there; a person can, and what the link leads to is not the directory the folder synced in. (3) A read that fails — of the record, of the anchor, of `.stfolder` or of the marker — refuses too (039), with a reason and a text of its own, "folder directory could not be checked: …", without a path. It is no finding about the directory: the vault shows a sync error that says VaultSync could not check its folder, never that the folder is a copy, and the next `CheckPath` — the next scan, at the latest the next rescan a minute later — asks again. The anchor too: an anchor the start could not read is read again by the next check, so the folder goes on once the read works, without a restart. The record is read first: a record from 3.0.x could only let the folder through, so no failed read of the anchor stops such a folder. (4) While refused, the folder stays in error: nothing in its directory is scanned, nothing is pulled into it, and no filter is written into it. One thing still reaches its index, as it does upstream for any folder: a peer's request for a block that the file at that path no longer matches marks that entry to be scanned again, and the peers see it as invalid until a scan is allowed. Nothing is lost by it and no version goes out. (5) The check reads, and writes nothing at all: not the record, not an index ID, not the anchor, nothing in the folder. It holds only a read of the engine's key-value store; it reads the anchor without making the file, and takes the folder's local index ID from what the bridge took from the engine at the start and with every add, accept, re-point and record write, because the engine's own read makes an index ID where there is none. Where it cannot decide without a write, it decides without: an index ID it does not know, or an anchor that is gone, means no record applies — as at the next start, which makes a new anchor, or for a folder added again, whose new index no old record names. What needs making is made at the start or in the reconcile. A record changes only in the path reconcile, under the bridge's lock with its configuration-change guard, and with an add, an accept or a re-point, as before. The reconcile gives a folder with no record that applies one; writes every record from 3.0.x in this version's shape ("The update"); adds `.stfolder`'s number to a record that waits for it once the recorded marker is there; and where the record's `.stfolder` is the one at the path and its marker file has another number, writes only the marker's number. The repair (`SetFolderPath`, 063) still holds every record, whatever its shape, to its marker; the marker's number it compares is still one read inside the directory the folder synced in. (6) Nothing is paused, moved, deleted or re-pointed. The check asks the record and the directory each time — it keeps only the anchor's file number and the snapshot of index IDs — so the folder goes on by itself once its own directory is back in its place, and stays stopped for as long as a copy lies there. (7) The vault's card under Sync Issues and its page say that the folder in the vault's place is not the folder the vault synced in, most likely a copy put there, that VaultSync does not sync it, and the way on: if the vault's own folder still exists, move the copy out of its place and put the vault's folder back; otherwise remove the vault and accept it again in a folder of its own, never combined with the copy (002, #331). The copy stays as it is.

**The update.** Two fields join the record under the same key (`vaultsync/folder-storage/1/`): `stfolder`, and `strict`, which every record this version writes carries. A record written by 3.0.x has neither and is read as before. Its marker decides the repair, as in 3.0.x. The engine's check holds such a record to nothing, so the first launch after the update never refuses a vault, also when a read fails. The first reconcile after the update writes every such record in this version's shape, whatever the folder's state:

- *The folder there with the recorded marker:* `.stfolder`'s number is added, read with that marker. Nothing is lost or taken.
- *The folder there with another marker, or without one:* nothing on the iPhone can tell a copy put in the vault's place before the update from the vault's own directory whose marker was made anew or went missing. The folder goes on, and the reconcile records what is there — `.stfolder`'s number with the marker there, or with the recorded marker where there is none. Such a copy is taken, once, as 3.0.x would have taken it.
- *The folder not there* — its path gone, `.stfolder` missing, a link or a file in its place, or out of the app's reach: the record keeps its marker and waits for `.stfolder`. Until then the folder is held to that marker: only a directory whose marker has the recorded number passes, and the next reconcile completes the record from it; anything else at the path is refused as a copy. That is what 3.0.1's repair asked of a directory found under another folder, now asked of one at the folder's own path, where 3.0.1 asked nothing.

None of the three takes or refuses more than 3.0.1 does. A read error other than these leaves a record as it is until a reconcile whose read answers. A version that does not know the fields reads the rest as it always did — 3.0.1 decodes with `json.Unmarshal` into a type with the marker, the index and the anchor only, so it skips the rest, and an empty `stfolder` is not written — and drops them on its next write; the update after it writes them again, the same way. Two reconciles in a row leave the same record (`TestIssue329_AVersionThatDoesNotKnowTheFieldReadsAndDropsIt`, `TestIssue329_ARecordOfAFolderThatIsNotThereIsHeldToItsMarker`).

**Why.** A copy in the folder's place and a copy found under another folder are one mistake, and 063 caught it only where the bridge moves a folder. `CheckPath` is the one place every scan, pull and commit passes, also while the engine runs — where the watcher sees a replacement at once and no check at the start can reach it — and the engine asks it where it reads the folder's directory anyway, for scans and pulls in the folder's own goroutine, so no start of the bridge reads a path the user chose while it holds its lock (#315's second review moved exactly that out). The check takes no bridge lock. No content is read: the directory a folder synced in is never refused for anything that changed in it. The question is about `.stfolder` and not about the marker file, because a marker file made anew or gone inside the vault's own `.stfolder` must not stop a vault whose owner did nothing — where storage can renumber a file is not measured — and a copy cannot bring the vault's own `.stfolder` along. The answer reads the record and the index ID from the engine's database each time instead of a copy in memory: one rule with no second state to keep current, at a cost `TestIssue329_WhatTheCheckCosts` measures — asked a handful of times per scan, once per commit and not per file.

**Rejected alternatives.** *Pausing the folder at the start, once (002's form).* A pause in `config.xml` outlives what caused it: a user who puts the vault's own folder back still has a paused vault, and VaultSync has no control to resume one, so the only way out would be the removal and a second download. "Once" needs a record of its own that a resume would have to clear, the marker reads would run inside the start under the bridge lock, and a replacement while the engine runs stays open. *The marker file as the engine's question.* It refused a healthy vault for good when its marker file was made anew or gone, and told its owner to remove it. *The vault's directory as the witness instead of `.stfolder`.* Both kept their numbers on every measured move and changed them on every measured copy; `.stfolder` is what a copy must carry to be scanned at all, and it also catches a copy's contents pasted into the vault's own directory together with the copy's `.stfolder`. *A button to go on in the copy.* It is the act that loses the notes, nothing on a card lets anyone judge it, and what the copy holds is kept by the second way out: remove, accept again in a folder of its own, copy over by hand. *Keeping the record following the live directory and comparing once at the start:* the reconcile that follows every start would write the copy's number before the next scan asks.

**Assumptions, and what showed them.** *A move keeps the numbers of the vault's directory, its `.stfolder` and its marker; a copy changes all three, or carries no `.stfolder`:*

| Operation in Files | Vault directory | `.stfolder` | Marker file |
|---|---|---|---|
| Move, Copy with "Move Item Here", drag and drop — simulators, iOS 18.0, 26.4, 26.5 | same | same | same |
| Copy and Paste, Duplicate — the same simulators | new | none | none |
| Copy and Paste into an app's folder — iPhone, iOS 27.0.1 | new | new | new, same content |
| Move out to another folder and back — the same iPhone | same | same | same |

The engine writes the marker only when `.stfolder` is missing (`CreateMarker`, read in the engine in use). `TestIssue329_TheVaultsOwnFolderIsNeverRefused` takes a vault through pulls, notes written on the device, filter writes, the reconcile's note, its marker file made anew, a container move with its re-point, its marker file gone and six stops and starts: the check is asked all along and never refuses. Taken as given: no other app on the iPhone rewrites a hidden entry of the vault. *Records written by 3.0.x name the directory each reachable folder synced in at its last reconcile:* they followed the live directory until this decision. **Nothing was measured on iCloud Drive or on another file provider.** Whether any storage gives a directory a new number without a copy is open and is measured on a device before the release that ships this; a vault on such storage would stop with this card, and the second way out applies. A vault moved to another storage location and moved back into its own place can arrive as new files (#337) and gets this card; what #337's measurement brings decides both checks, because both rest on file numbers.

**Not covered.** The vault's own `.stfolder` moved into a copy: the copy then has the recorded `.stfolder` and cannot be told from the vault's own directory (pinned in `TestIssue329_ACopyWithTheOriginalsMarkerIsTakenForTheVault`). A vault's visible files replaced by a copy's while its own `.stfolder` stays: that is the vault's own directory with its notes changed by hand. The Files app shows neither hidden entry. The repair does not ask `.stfolder`: it decides by the marker alone, as 063 decided, so a copy whose `.stfolder` holds the vault's marker — hard-linked or moved over — is taken by a repair once the vault's own directory is gone, and a vault whose marker file was made anew and that moves before a reconcile has recorded the new marker is refused by a repair as a copy. A repair that asks both would change 063's rule and needs a measurement and a record of its own. A copy put in place where no record with the field applies: on an install that comes from a version without records, before its first reconcile; after a restore or a migration (063); and, once, a copy put in place before the update to this version (above). A copy that 3.0.x already synced as the vault: its record now names the copy, and what it sent is sent. A replacement in the instant between a commit's check and the commit. A folder with nothing in its index whose directory is gone is made again by the engine at its next start, with a new `.stfolder` (#338): it gets this card, though nothing was copied. A marker file gone from the vault's own `.stfolder` is not made again; the folder syncs on, and the repair refuses it as "marker missing", as it does any folder without its marker file.

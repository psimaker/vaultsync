# 084 — The engine syncs a folder only in the directory it synced in

**Context.** Decision 063 records which directory a folder synced in — the file number of its marker, with the folder's index ID and an anchor — and asks the record where the bridge re-points a folder whose directory is gone. A copy put in the folder's own place needs no re-point (#329): in the Files app the vault's folder is deleted and an earlier duplicate is renamed to its name. The path is alive and holds a `.stfolder`, so the engine's `CheckPath` passed, and the folder's next scan took every difference for a change made on this iPhone: what the copy lacks went out as deletions, its older notes as the current versions, to every device. `TestIssue329_ACopyInTheVaultsOwnPlaceKeepsThePeerWhole` showed it against a real peer for a copy put in place while VaultSync is closed, `TestIssue329_ACopyPutInPlaceWhileTheEngineRunsKeepsThePeerWhole` while the engine runs, where the watcher's scan sent the copy out ten seconds after it was put in place. The record did not even keep what it knew: the path reconcile noted every live folder's marker, so the first reconcile after a start wrote the copy's number over the vault's.

**Decision.** (1) Whenever the engine's `CheckPath` has found a folder's directory and its marker entry — before every scan, every pull and every commit of scan results, and before every write of the folder's filters (069) — it asks whether that directory is the one the folder synced in (fork patch 007: a check the bridge installs before the engine starts and removes once it has stopped). The bridge answers by 063's rule, in one function both callers share. A record that applies — same anchor, same index ID — and at the folder's path a marker with another file number, or no marker file: refused with "folder directory is not the directory this folder synced in", which the app shows as a copy in the vault's place. No record, or one that does not apply: the marker has decided, as before. (2) A read that fails — of the record, the anchor, the index ID or the marker's file number — refuses too (039), with a reason and a text of its own, "folder directory could not be checked: …" without a path. It is no finding about the directory: the vault shows a sync error that says VaultSync could not check its folder, never that the folder is a copy, and the next `CheckPath` — the next scan, at the latest the next rescan a minute later — asks again. (3) While refused, the folder stays in error: nothing in its directory is scanned, nothing is pulled into it, no filter is written into it, and the index its devices have stays as it was. (4) A live folder's record no longer follows its directory. The path reconcile writes a record only for a folder that has none that applies, and never over one it cannot read; a record that applies changes only with an act on the folder — an add, an accept, a re-point — as before. (5) Nothing is paused, moved, deleted or re-pointed. The check keeps no state of its own and asks the record and the directory each time, so the folder goes on by itself once its own directory is back in its place, and stays stopped for as long as a copy lies there. (6) The vault's card under Sync Issues and its page say that the folder in the vault's place is not the folder the vault synced in, most likely a copy put there, that VaultSync does not sync it, and the way on: if the vault's own folder still exists, move the copy out of its place and put the vault's folder back; otherwise remove the vault and accept it again in a folder of its own, never combined with the copy (002, #331). The copy stays as it is.

**Why.** A copy in the folder's place and a copy found under another folder are one mistake, and 063 caught it only where the bridge moves a folder. `CheckPath` is the one place every scan, pull and commit passes, also while the engine runs — where the watcher sees a replacement at once and no check at the start can reach it — and the engine asks it where it reads the folder's directory anyway, for scans and pulls in the folder's own goroutine, so no start of the bridge reads a path the user chose while it holds its lock (#315's second review moved exactly that out). The check takes no bridge lock. No content is read: the directory a folder synced in is never refused for anything that changed in it. The answer reads the record and the index ID from the engine's database each time instead of a copy in memory: one rule with no second state to keep current, at a cost `TestIssue329_WhatTheCheckCosts` measures — asked a handful of times per scan, once per commit and not per file.

**Rejected alternatives.** *Pausing the folder at the start, once (002's form).* A pause in `config.xml` outlives what caused it: a user who puts the vault's own folder back still has a paused vault, and VaultSync has no control to resume one, so the only way out would be the removal and a second download. "Once" needs a record of its own that a resume would have to clear, the marker reads would run inside the start under the bridge lock, and a replacement while the engine runs stays open. *A button to go on in the copy.* It is the act that loses the notes, nothing on a card lets anyone judge it, and what the copy holds is kept by the second way out: remove, accept again in a folder of its own, copy over by hand. *Keeping the record following the live directory and comparing once at the start:* the reconcile that follows every start would write the copy's number before the next scan asks. *Calling a failed read a copy:* it would send people to remove a vault that is their own, for a read that works again a moment later.

**Assumptions, and what showed them.** *A folder's own marker keeps its file number for as long as its directory exists:* the engine writes the marker only when the `.stfolder` entry is missing (`CreateMarker`, read in the engine in use), and a move or a rename on one volume keeps the number (063's measurements). `TestIssue329_TheVaultsOwnFolderIsNeverRefused` takes a vault through pulls, notes written on the device, filter writes, the reconcile's note, three stops and starts and a container move with its re-point: the check is asked all along and never refuses, and the record never changes. Taken as given: no other app on the iPhone rewrites a hidden entry of the vault. *Records written by 3.0.x name the directory each reachable folder synced in at its last reconcile:* they followed the live directory until this decision, so the first start of this version compares with what was there; no format changes and nothing is migrated. Not measured, and only a device shows it: whether a file provider — iCloud Drive — ever gives a file it holds a new number without anyone copying it; a vault there would then stop with this card, and the second way out applies. A vault moved to another storage location and moved back into its own place arrives as new files (#337) and gets this card; what #337's measurement brings decides both checks, because both ask one rule.

**Not covered.** A copy whose `.stfolder` was moved over from the vault's own folder carries the recorded number and cannot be told from the vault's own folder with its notes changed by hand (pinned in `TestIssue329_ACopyWithTheOriginalsMarkerIsTakenForTheVault`); the Files app does not show that entry. A copy put in place where no record applies: on an install that comes from a version without records, before its first reconcile, and after a restore or a migration (063). A copy that 3.0.x already synced as the vault: its record now names the copy, and what it sent is sent. A replacement in the instant between a commit's check and the commit. A folder with nothing in its index whose directory is gone is made again by the engine at its next start, with a new marker (#338): it gets this card, though nothing was copied.

# 039 — Bridge reads that gate a decision fail closed

**Context.** Two bridge reads answered a failure with a default. `AcceptPendingFolder` treated a failed read of the pending offers like "no offer" and created a local-only folder that no peer shares; `GetFolderIgnores` returned an empty list for an unreadable `.stignore`, so the Sync Filters screen showed "no filters" while filters existed (#182).

**Decision.** A read whose result gates a user-visible decision or a write never substitutes a default on failure. The error reaches the caller: the accept is refused with the read error; the ignores read returns `{"error": …}` (OS error only, no path), which the app renders as "unavailable" and which every read-modify-write flow treats as "do not write". A successful read that finds nothing — no offer, no `.stignore` — keeps its existing meaning.

**Why.** A default that looks like a legitimate answer hides the failure exactly when the user decides or the app writes, and the wrong write then propagates: an unshared vault that looks accepted, an emptied `.stignore`.

**Rejected alternative.** Keeping the defaults and logging the error. Logs never reach the decision; the UI still claims a state that is not true.

**Since #464 (2026-11-27): the list of offered shares.** `GetPendingFoldersJSON` answered `[]` when no engine ran and when the engine could not read its offers — the same bytes as "nothing is offered". The app cuts its record of shares set aside with "Ignore for Now" down to the list it reads, so such an answer cleared the record, and once the list was read again the automatic accept took the shares the user had set aside. The engine can stop between the poll's check and its read: a background run ends while the foreground poll goes on, or the engine exits. Decision: a read of the offers that fails, or that a stopped engine answers, is never a list. The bridge answers `{"error": "syncthing not running"}` or `{"error": "read pending folder offers: …"}`; a successful read keeps `[]` for "nothing is offered". No answer of that file names a path: an OS error's path is dropped there and in the accept's errors (safety rule 6). The app counts an answer only when one engine ran for the whole read — the same engine generation, not zero, before and after it (`SyncthingManager.pendingFolderRead`) — and a poll's read that began before a stop or a reset of the manager is not applied after it (the refresh after an accept reads and applies in one step, so nothing comes between). Only such a list replaces the list and cuts the record; any other answer changes nothing. A persisted record is cut down only from a list read in full by one running engine; the record of removed folders (decision 006) is never cut by a read. An unreadable list keeps the list and the record, and while the manager polls — which reads again — every place that shows the list says it could not be read: Pending Shares, onboarding, the setup checklist and the Hub step; the rating prompt waits (decision 067). Nothing is accepted from the rows last read meanwhile: the automatic pass waits and runs again once a list is read, and a tap is told to try again in a moment, with no failure recorded. *Rejected:* keeping `[]` and checking `isRunning()` in the app before the read — the engine can stop after the check, which is the window this closes; cutting the record only after several empty lists in a row — a stopped engine answers the same every time, and the record would still go; accepting from the last rows read — the bridge reads the offers again and refuses each, and the refusals would read as failures of the shares.

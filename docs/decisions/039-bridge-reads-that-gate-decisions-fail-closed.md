# 039 — Bridge reads that gate a decision fail closed

**Context.** Two bridge reads answered a failure with a default. `AcceptPendingFolder` treated a failed read of the pending offers like "no offer" and created a local-only folder that no peer shares; `GetFolderIgnores` returned an empty list for an unreadable `.stignore`, so the Sync Filters screen showed "no filters" while filters existed (#182).

**Decision.** A read whose result gates a user-visible decision or a write never substitutes a default on failure. The error reaches the caller: the accept is refused with the read error; the ignores read returns `{"error": …}` (OS error only, no path), which the app renders as "unavailable" and which every read-modify-write flow treats as "do not write". A successful read that finds nothing — no offer, no `.stignore` — keeps its existing meaning.

**Why.** A default that looks like a legitimate answer hides the failure exactly when the user decides or the app writes, and the wrong write then propagates: an unshared vault that looks accepted, an emptied `.stignore`.

**Rejected alternative.** Keeping the defaults and logging the error. Logs never reach the decision; the UI still claims a state that is not true.

**Since #464 (2026-11-27): the list of offered shares.** `GetPendingFoldersJSON` answered `[]` when no engine ran and when the engine could not read its offers — the same bytes as "nothing is offered". The app cuts its record of shares set aside with "Ignore for Now" down to the list it reads, so such an answer cleared the record, and once the list was read again the automatic accept took the shares the user had set aside. The engine can stop between the poll's check and its read: a background run ends while the foreground poll goes on, or the engine exits. Decision: a read of the offers that fails, or that a stopped engine answers, is never a list. The bridge answers `{"error": "syncthing not running"}` or `{"error": "read pending folder offers: …"}` (the engine's error without an OS error's path; the scan reads every offer, so it names no folder or device); a successful read keeps `[]` for "nothing is offered". The app counts an answer only when one engine ran for the whole read — the same engine generation, not zero, before and after it (`SyncthingManager.pendingFolderRead`) — and only while the manager is still attached to that engine: a read that began before a stop or a reset is not applied after it. Only such a list replaces the list and cuts the record; an unreadable list keeps both and is said where the list is shown (Pending Shares, onboarding, the setup checklist), and any other answer changes nothing. A persisted record is cut down only from a list read in full by one running engine. The record of removed folders (decision 006) is never cut by a read. *Rejected:* keeping `[]` and checking `isRunning()` in the app before the read — the engine can stop after the check, which is the window this closes; cutting the record only after several empty lists in a row — a stopped engine answers the same every time, and the record would still go.

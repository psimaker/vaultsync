# 049 — The desktop agent's control socket: HTTP over a unix socket, device pause, the flag flow for pairing

**Context.** M4 (#176, decision 048): the menu-bar app shows exactly what `vaultsync status` shows and decides nothing — it needs the running agent to answer status, pause, resume and "start pairing". The agent owns the engine (046) and runs headless, as a LaunchAgent or a systemd user unit.

**Decision.** `vaultsync run` serves `GET /v1/status`, `POST /v1/pause`, `POST /v1/resume` and `POST /v1/pair` as JSON over HTTP/1.1 on a unix socket in VaultSync's folder (`agent.sock`, mode 0600 in the 0700 folder; a folder too deep for a socket address falls back to a 0700 folder under the temporary directory, recorded in `agent.json`). No token: the file permissions are the authentication, as for `agent.json` and the engine's API key. The socket lives exactly as long as the engine lock is held; an engine that cannot have one still runs. `vaultsync status` asks the agent first and the engine directly when no agent answers; `pause` and `resume` ask only the agent. **Pause** pauses every Hub device in the engine — a device setting the engine keeps across its own restarts and the service's, until `resume` (a `vaultsync start` does not resume it; `stop`/`start` are the service's state, pause/resume the engine's). It stops the connections, not the folder workers: changes the engine had already taken in may still be applied, so the CLI says so, and status replaces only the connection-derived states with "paused on this computer" and keeps errors, the folder's own pause, and work in progress visible. The PATCH is sent even to a device that already reads as paused, because the engine applies a change before saving it. Pause and pairing share the pairing lock, and the pairing flow refuses while paused, for the terminal and the socket alike. **Pair** is the flag flow of `vaultsync pair`, non-interactive, run by the agent with the same guards and the same consent (`yes`); the answer carries the output, the refusal and the menu the terminal would show, so a caller chooses and asks again — the code stays valid until the Hub expires it (only wrong codes lock it), so no session is held between calls. The service's environment is not the shell's: `setup` and `pair` record the shell's `XDG_STATE_HOME`, `XDG_CONFIG_HOME` and `APPDATA` in `agent.json`, and a pairing run by the service looks in both environments for the user's own Syncthing, Obsidian's registry and the cloud clients' settings, so it refuses what the terminal refuses.

**Why.** One code path for the terminal and the menu: no second status or pairing logic to keep safe. HTTP and JSON are in the standard library on both sides and versioned by path. Device pause changes no folder setting a user or the Hub may have made. A stateless pair keeps the agent free of session state, timeouts and a cancel path.

**Rejected alternatives.** A TCP port on loopback (any account on the computer could reach it). A line protocol of our own (nothing net/http does not give). Folder pause for "pause" (would resume folders paused on purpose; per-folder pause stays the user's own setting). Pausing the engine process (without the agent, status could not tell a pause from a crash). A pairing session kept open across calls (state, timeouts and a tray that must cancel it, for nothing while the code stays valid).

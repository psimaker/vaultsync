# 063 — A folder's directory is known by its marker's file number; the marker alone cannot tell a copy

**Context.** 003 made the `.stfolder` marker the proof that a directory is a folder's own: `SetFolderPath` moved a folder whose directory is gone to `<selected folder>/<its path>` when the directory there held the folder's marker file. A copy made by hand carries that marker (#315, seen on a device: a copy made in the Files app keeps `.stfolder` and `.stignore`). A vault copied under another folder, the first folder deleted later, the other one selected: the folder was continued in the copy, and its first scan there sent out what had synced since the copy was made, as deletions and as the old versions. `TestIssue315_ACopyWithTheFoldersMarkerIsNotItsStorage` shows it on a real peer.

**Decision.** (1) While a folder's directory is there, the bridge records the file number (inode) of the folder's marker, with the folder's local index ID and the file number of an anchor — a file beside the engine's configuration, created once and never written again. The record lies in the engine database's key-value store and is written by the bridge only: at engine start, when a folder is added or accepted, and after a re-point. A folder whose directory is gone keeps the record it has. (2) `SetFolderPath` keeps the marker check and refuses while the folder's own directory exists (003). Then: a record that applies — same index ID, same anchor — and the recorded number at the target: re-point, whatever changed in the directory. A record that applies and another number: refuse (`FolderStorageMismatchError`), the directory is a copy. No record, another index ID or another anchor: the marker decides, as before. No content is read and the check runs under the bridge lock. Something in a record's place that is no record counts as none; a read that fails refuses (039). (3) A refusal leaves the folder where it is. The vault's card and its own page say that the folder found is a copy, and the way on: select the folder that contains the vault's own folder, or remove the vault and accept it again in a folder of its own — never combined with the copy (002, #331).

**Why.** What makes a directory the folder's is that the folder synced in it, not what it holds: the vault's own directory may hold any number of changes the engine has not seen, and a copy may hold exactly what the index says. The file number tells the two apart without reading anything, so the folder's own directory is never refused for its content.

**Assumptions, and what showed them.** *A copy gets a new file number, a move keeps it:* measured on APFS for `cp -R`, `cp -Rp`, a clone, `FileManager.copyItem`, `mv` and a renamed parent; @@FILES@@ *A restore or a migration creates every file anew, the anchor included, so no record from before applies:* `TestIssue315_AfterARestoreTheMarkerDecides`, where a restore is a copy of everything. *A folder removed and added again has another index ID* (the engine drops a removed folder's database), *the marker is there when the add returns, and the engine takes the marker of a removed folder with it when it can reach the directory:* `TestIssue315_AVaultAddedAgainDoesNotGoBackToWhatItLeftBehind`. Taken as given: a container whose path changes keeps its file numbers, and APFS hands no number out twice. A hard link or a symbolic link to the marker would carry its number; the Files app makes neither. Each of these fails toward the card or toward the marker deciding as before — nothing is re-pointed that the marker alone would have refused.

**Rejected alternative.** *Proving that the directory agrees with the folder's index* — every recorded entry there with its size and time, every deleted one absent — was the first form of this record and fell in review. It refuses the folder's own directory after any change Obsidian made since the last scan, which on iOS is the ordinary state, and the way out it then prescribes, accepting the share again and combining, lets the older text of a copy replace notes only this iPhone wrote (#331). A copy passes it for as long as it "agrees", and that is judged against the local index alone: the copy's own ignore rules, files whose time alone differs (#332) and deletions the database has since forgotten (#333) all slip through. A vault that syncs the selected folder itself had no way out of the refusal. And it read whole vaults outside the bridge lock, where the folder could change under it. *Going on in the copy with the folder paused, for the user to decide there:* the folder would already be re-pointed (003).

**Not covered.** A restore or a migration followed by selecting a folder that holds an earlier copy: the marker decides, as before (pinned in the restore test). A folder whose directory was already gone when the first version that writes records starts. A copy put in the folder's own place, under its own path (#329): a live folder's record follows the directory the engine scans. The record is derived state — losing it costs this protection, never a note.

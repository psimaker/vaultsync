# 097 — The Hub's state file has one writer at a time and keeps its owner

**Context.** The Hub keeps its pairing state in one file: the open code (as its password scalar), the count of wrong attempts on it (the lockout of decision 036) and the devices it paired. Two processes change it. The server (`vaultsync-hub serve`) does so when it records a pairing or counts a wrong attempt; a command does so when the operator runs it (`vaultsync-hub code`, and later `device remove`, decision 094). Each change is a fresh read, the change, then a temp file and a rename, ordered by a mutex that exists only inside one process. When two processes changed the file at the same moment, the later rename undid the other's change: a new code could be replaced by the old one, a recorded pairing could vanish, a failed attempt's count could be lost. Two stores on one file lost about half of 150 to 300 changes each (#490). A command run as root (`docker compose exec -u 0`, or a program on the host) also left the file owned by root and readable by root alone, so the server answered every pairing with "hub state unavailable".

**Decision.**
1. **One lock for every writer.** Every read-modify-write of the state file, in whichever process, holds an exclusive `flock(2)` on a lock file beside it (`<state>.lock`) from its read to its rename, inside the in-process mutex. Readers take no lock: a rename always shows a whole file. Every later writer of the file goes through `stateStore.update`, or takes the same lock the same way.
2. **Both files belong to the Hub's service user.** That user is read from what is on disk (`stateTarget`): the state file's owner, or, for a file left to root in a folder another user owns, the folder's owner; a new file goes to the folder's owner when root makes it. The lock file is made 0600, opened for reading and writing (an exclusive lock on NFS needs a descriptor open for writing), never through a link, and only when it is a regular file. A write by root hands the new state file, and a lock file of another owner or mode, to that user, on the open descriptor, so nothing is made or changed at a link's target. A write by any other user whose file would belong to someone else is refused (`decideOwner`), and the words say how to hand the state back as root: `chown --reference=hub` on the host, or `docker compose exec -u 0 hub vaultsync-hub code`, whose write as root gives both files to their folder's owner.
3. **Fail closed.** A write that cannot get the lock within five seconds fails and says the state is busy. So does a lock file that cannot be opened or made, is a link or no regular file, an owner that cannot be kept, and storage on which `flock` is refused. On such storage (a network mount without lock support) nothing that writes the state works: no code opens and no device pairs, and the words say to keep the Hub's folder on a local disk or mount its storage with lock support. In none of these cases does the write go on without the lock, and there is no fallback.
4. **The count of wrong attempts.** It is kept per code, in the server's memory and in the state file. An attempt's check against the limit, its verification and its count are one step under one lock: the new count is the higher of the two, plus one. Memory takes it and the file is written with it, so each attempt counts once, also when the write fails. An attempt on a session from an older code counts against that code only. The limit on wrong codes is held at every attempt.
5. **A pairing's record comes first.** It is written before the device is registered or a vault created. A pairing whose record cannot be written is refused and leaves nothing behind. A later step that fails says in its answer and the log what exists by then.
6. **Windows** keeps only the in-process lock, behind a build tag. `vaultsync-hub` is built there for `pair`, which writes no Hub state; a Hub runs on Linux. CI builds and vets the Hub for Windows on every change.

**Why.** The server re-reads the file inside every write and keeps nothing of it between requests. Once every writer holds the same lock across its read and its rename, no write can rest on a stale read. A lock on the state file itself would not hold: each write replaces that file by a rename. The lock file belongs to the one user who may write the state, so no other account on the host can open it and hold the lock, and the owner rule makes sure a write by root never shuts that user out.

**Rejected alternatives.**
- *The command asks the server to make the change.* The server has no control channel, and its only listener is the pairing port on the LAN, which must take no administrative request.
- *A lock inside the state file.* The rename replaces the file, and with it any lock on it.
- *A silent fallback to the in-process lock* when `flock` fails or waits too long. It would bring back the lost update without anyone knowing.
- *A lock file open to every writer* (0644, opened read-only). Any account on the host could hold it and stop every write, and NFS refuses an exclusive lock on a descriptor not open for writing.
- *An exact count by reserving in memory and writing later.* Writes that arrive out of order then count one attempt twice.

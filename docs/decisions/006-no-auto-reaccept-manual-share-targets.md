# 006 — Removed vaults are never auto-re-accepted; manual share targets persist

**Context:** While a peer still shares a folder, its offer reappears moments after local removal, and the auto-accept loop pulled it straight back in — "Remove Vault" was silently undone, and the #52 manual target picker was unreachable because a share never stayed pending long enough to act on.

**Decision:** `removeFolder` records the folder ID as user-removed; auto-accept skips recorded shares (they stay visible under Pending Shares until explicitly accepted, which lifts the record). A manually picked target (#52) is stored per folder ID, deliberately survives removal, and is honored by every later accept; an override that became unsafe is refused with guidance. Only empty folders (nothing but `.obsidian`) are eligible as existing targets.

**Why:** This is [002](002-manual-recovery-doctrine.md) applied to accept: re-accepting user data is never automatic once the user expressed intent by removing the folder — recovery and re-adding stay explicit user actions. Silently falling back to the share-label default when the chosen target is unsafe would split one vault's content across two directories.

**Rejected alternatives:** A global "ask before accepting shares" toggle — changes the default for every share and still cannot stop the instant re-accept after removal. Pruning the user-removed set against currently pending offers — would drop the record before the offer reappears (it can take a reconnect), re-enabling the zombie re-accept. Silent fallback to the label default on an unsafe override — hides a data-placement decision from the user.

**Since #343: the record is written before the engine is asked.** A removal can go ahead after the bridge answered with a failure: the engine takes the change into its configuration first and then waits for its services — the model stops the folder and drops its database there — while the bridge waits at most 30 seconds (`lifecycleTimeouts.configCommit`, decision 038). Recorded only on success, such a removal left no record, and the share offered again was accepted automatically. So `removeFolder` records the folder ID, and saves the record, before it calls the bridge, and keeps it whatever the bridge answers; it is never moved back into the success branch, and as before only an explicit accept lifts it. A record for a removal that never landed costs nothing: a configured folder is not offered as a new share. The bridge's answers: `""` once the folder is gone from the engine's configuration in memory, also when the engine's own cleanup outlasted the wait; `FolderRemovalNotConfirmedError()` for a removal that did not reach the configuration within the wait — queued behind another change, once that one is through it lands or the engine refuses it, and if the engine stops first it never lands — which the app tells in a note, asking to remove the vault again if it is still listed; the engine's refusal otherwise; `FolderNotFoundError()` for a folder that is not configured, which the app takes for a removal that is done. Both texts are read from the bridge. What only adds caution runs before the bridge is asked: the record, and dropping a remembered folder name's consent when a copy was found in the vault's place or the paths are not settled (#315). What says the folder is gone — its path record, its auto-pause record, the Obsidian notice's choice, the copy finding — runs only on `""` or `FolderNotFoundError()`, because a folder that stays configured still needs them. *Not covered.* `""` is not "on disk": the engine saves its configuration only once its services are through with the change, and while it waits for the folder to stop, it has not (the wrapper's save timer, #151). An app ended in that window finds the vault configured again at the next start, with no note; nothing is accepted by itself, because the record exists, and the person removes the vault again. A removal answered "not confirmed" that lands later leaves its path record, its auto-pause record and the Obsidian notice's choice behind — the folder list drops the vault within seconds, so nobody asks for the removal again — and none of them can mislead a later accept: an accept writes the path record anew, the auto-pause record counts only for an overlap the bridge refuses (001), and the notice's choice only for a vault that syncs the selected folder itself, a place no new accept may take (rule 9, 058). *Rejected:* recording on success and on the not-confirmed answer only — a removal can land while the bridge still waits on the main thread, and an app ended in those seconds left it without a record.

**Since #341: an accept is answered by whether it reached the configuration, waits as an accept while it is queued, and is never sent twice.** An accept can be tapped while the engine's configuration queue still holds another change — the rest of the removal whose share #341 offers again at once, or any other — and the bridge waits for an accept at most 30 seconds, as for a removal. An accept still queued then was answered like a refusal although it landed later, and a second tap queued a second accept of the same share. `AcceptPendingFolder` answers `""` once the folder is in the engine's configuration in memory at the path this accept asked for, also when the engine's services are still starting it — a folder of the ID at another path is an earlier accept, and this one was refused as its duplicate; `FolderAcceptNotConfirmedError()` for an accept still queued when the wait ends — it lands once the change before it is through, or the engine refuses it; the engine works through its queue while it stops and saves what it applied, so it may also be configured at the next start, and only a stop that ends before the change is taken loses it — and the same text, at once and without creating or queueing anything, for every further accept of that share until the engine has taken the queued one from its queue or has been started anew (`AcceptInFlight`). A queued accept counts as a folder for the floors that keep two folders out of one directory (001): `AcceptPendingFolder`, `AddFolder` and `SetFolderPath` hold the path against it as against a configured folder, with the same comparison and the same refusal, so a target a queued accept is headed for is taken, merge consent or not. The app keeps such a share waiting for its accept, in memory: the row shows the note under the title "Accept Not Confirmed Yet" with no failure look and without "Ignore for Now" or "Choose Vault…", neither of which could withdraw or move the queued accept; onboarding and the Hub's hand-off show it as being added; the automatic pass leaves it; a tap on it is settled first and never sends a second accept. The poll reads whether the engine still holds the accept before it reads the folder list, and settles it once the engine has taken it: configured at the accept's path, the accept landed, and what follows a confirmed accept runs then — the record of a removal is lifted as by any explicit accept, and the defaults and the first scan follow; not configured, the engine refused it, and the share is an ordinary pending one again, which the automatic pass may take. A tap that meets the folder already configured at the accept's own path is that accept having worked. Until the landing nothing that only a confirmed accept records is written: the record of a removal stays, so the automatic pass leaves the share alone; a chosen folder name is not recorded as consent, before or after; the path mapping is left to the launch reconcile, which fills it in for a folder that landed. *Not covered.* A queued accept is checked when it is queued and lands without a second look: the selected folder may have changed meanwhile, files may have been put into its target, a path reconcile may have begun (007, 008, 058 to 060). The window is as long as the change ahead of it takes in the engine — the services stopping a removed folder and dropping its database, or any other change — which the bridge does not bound; the note asks to accept again after a minute, and an engine stop ends it, with the accept landed or lost. Closing it needs a check at the moment the engine applies the change: the engine calls `VerifyConfiguration` on every subscriber that implements it before it applies a change, so a verifier of the bridge's own could hold a queued accept against the configuration it lands in and refuse it there, without a fork patch. An accept that landed at a stop is configured at the next start, while the app forgot the share was waiting: the vault is listed and syncs, the share is gone from Pending Shares, and the record of an earlier removal stays — harmless while the folder is configured, and written anew by any later removal. *Rejected:* refusing every accept while a change is queued — the engine does not tell the queue's state, and a change of its own can queue at any time; keeping the refusal's answer for a late accept — it is the defect itself.

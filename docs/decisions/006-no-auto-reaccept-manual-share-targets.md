# 006 — Removed vaults are never auto-re-accepted; manual share targets persist

**Context:** While a peer still shares a folder, its offer reappears moments after local removal, and the auto-accept loop pulled it straight back in — "Remove Vault" was silently undone, and the #52 manual target picker was unreachable because a share never stayed pending long enough to act on.

**Decision:** `removeFolder` records the folder ID as user-removed; auto-accept skips recorded shares (they stay visible under Pending Shares until explicitly accepted, which lifts the record). A manually picked target (#52) is stored per folder ID, deliberately survives removal, and is honored by every later accept; an override that became unsafe is refused with guidance. Only empty folders (nothing but `.obsidian`) are eligible as existing targets.

**Why:** This is [002](002-manual-recovery-doctrine.md) applied to accept: re-accepting user data is never automatic once the user expressed intent by removing the folder — recovery and re-adding stay explicit user actions. Silently falling back to the share-label default when the chosen target is unsafe would split one vault's content across two directories.

**Rejected alternatives:** A global "ask before accepting shares" toggle — changes the default for every share and still cannot stop the instant re-accept after removal. Pruning the user-removed set against currently pending offers — would drop the record before the offer reappears (it can take a reconnect), re-enabling the zombie re-accept. Silent fallback to the label default on an unsafe override — hides a data-placement decision from the user.

**Since #343: the record is written before the engine is asked.** A removal can go ahead after the bridge answered with a failure: the engine takes the change into its configuration first and then waits for its services — the model stops the folder and drops its database there — while the bridge waits at most 30 seconds (`lifecycleTimeouts.configCommit`, decision 038). Recorded only on success, such a removal left no record, and the share offered again was accepted automatically. So `removeFolder` records the folder ID, and saves the record, before it calls the bridge, and keeps it whatever the bridge answers; it is never moved back into the success branch, and as before only an explicit accept lifts it. A record for a removal that never landed costs nothing: a configured folder is not offered as a new share. The bridge's answers: `""` once the folder is gone from the configuration, also when the engine's own cleanup outlasted the wait; `FolderRemovalNotConfirmedError()` for a removal that did not reach the configuration within the wait — queued behind another change, it lands once that one is through, or never if the engine stops first — which the app tells in a note, asking to remove the vault again if it is still listed; the engine's refusal otherwise; `"folder not found"` for a folder that is not configured, which the app takes for a removal that is done. What only adds caution runs before the bridge is asked: the record, and dropping a remembered folder name's consent when a copy was found in the vault's place or the paths are not settled (#315). What says the folder is gone — its path record, its auto-pause record, the Obsidian notice's choice, the copy finding — runs only on `""` or `"folder not found"`, because a folder that stays configured still needs them. *Rejected:* recording on success and on the not-confirmed answer only — a removal can land while the bridge still waits on the main thread, and an app ended in those seconds left it without a record.

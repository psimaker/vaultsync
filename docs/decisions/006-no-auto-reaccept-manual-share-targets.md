# 006 — Removed vaults are never auto-re-accepted; manual share targets persist

**Context:** While a peer still shares a folder, its offer reappears moments after local removal, and the auto-accept loop pulled it straight back in — "Remove Vault" was silently undone, and the #52 manual target picker was unreachable because a share never stayed pending long enough to act on.

**Decision:** `removeFolder` records the folder ID as user-removed; auto-accept skips recorded shares (they stay visible under Pending Shares until explicitly accepted, which lifts the record). A manually picked target (#52) is stored per folder ID, deliberately survives removal, and is honored by every later accept; an override that became unsafe is refused with guidance. Only empty folders (nothing but `.obsidian`) are eligible as existing targets.

**Why:** This is [002](002-manual-recovery-doctrine.md) applied to accept: re-accepting user data is never automatic once the user expressed intent by removing the folder — recovery and re-adding stay explicit user actions. Silently falling back to the share-label default when the chosen target is unsafe would split one vault's content across two directories.

**Rejected alternatives:** A global "ask before accepting shares" toggle — changes the default for every share and still cannot stop the instant re-accept after removal. Pruning the user-removed set against currently pending offers — would drop the record before the offer reappears (it can take a reconnect), re-enabling the zombie re-accept. Silent fallback to the label default on an unsafe override — hides a data-placement decision from the user.

**Since #343: the record is written before the engine is asked.** A removal can go ahead after the bridge answered with a failure: the engine takes the change into its configuration first and then waits for its services — the model stops the folder and drops its database there — while the bridge waits at most 30 seconds (`lifecycleTimeouts.configCommit`, decision 038). Recorded only on success, such a removal left no record, and the share offered again was accepted automatically. So `removeFolder` records the folder ID, and saves the record, before it calls the bridge, and keeps it whatever the bridge answers; it is never moved back into the success branch, and as before only an explicit accept lifts it. A record for a removal that never landed costs nothing: a configured folder is not offered as a new share. The bridge's answers: `""` once the folder is gone from the engine's configuration in memory, also when the engine's own cleanup outlasted the wait; `FolderRemovalNotConfirmedError()` for a removal that did not reach the configuration within the wait — queued behind another change, once that one is through it lands or the engine refuses it, and if the engine stops first it never lands — which the app tells in a note, asking to remove the vault again if it is still listed; the engine's refusal otherwise; `FolderNotFoundError()` for a folder that is not configured, which the app takes for a removal that is done. Both texts are read from the bridge. What only adds caution runs before the bridge is asked: the record, and dropping a remembered folder name's consent when a copy was found in the vault's place or the paths are not settled (#315). What says the folder is gone — its path record, its auto-pause record, the Obsidian notice's choice, the copy finding — runs only on `""` or `FolderNotFoundError()`, because a folder that stays configured still needs them. *Not covered.* `""` is not "on disk": the engine saves its configuration only once its services are through with the change, and while it waits for the folder to stop, it has not (the wrapper's save timer, #151). An app ended in that window finds the vault configured again at the next start, with no note; nothing is accepted by itself, because the record exists, and the person removes the vault again. *Since #465 (decision 096), the bridge writes the removal to the file as soon as the engine has taken it, before it waits: `""` is "on disk", except for a write that failed and the race 096 names.* A removal answered "not confirmed" that lands later leaves its path record, its auto-pause record and the Obsidian notice's choice behind — the folder list drops the vault within seconds, so nobody asks for the removal again — and none of them can mislead a later accept: an accept writes the path record anew, the auto-pause record counts only for an overlap the bridge refuses (001), and the notice's choice only for a vault that syncs the selected folder itself, a place no new accept may take (rule 9, 058). *Rejected:* recording on success and on the not-confirmed answer only — a removal can land while the bridge still waits on the main thread, and an app ended in those seconds left it without a record.

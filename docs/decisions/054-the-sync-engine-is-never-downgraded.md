# 054 — The desktop agent never installs an older Syncthing than the one set up

**Context.** The agent installs the Syncthing its `pins.go` names, and `setup` and the service's `run` install it again whenever `agent.json` records another version (decision 046). With VaultSync for Mac (decision 053) the service runs whatever build sits in Applications, and an older one can get there without any VaultSync command — a Finder drag of an old zip, a Time Machine restore; an old copy or an old download can run `setup` too. That older build would put its older Syncthing over the database and config a newer Syncthing wrote (#264).

**Decision.** `ensureEngine` (setup) and `run` refuse when `agent.json` records a newer Syncthing than the pin (`engineNewer`, vX.Y.Z, a suffix aside) — or a version they cannot read, or `agent.json` is in a newer format (`errStateNewer`): the guard fails closed — nothing is changed, setup says which versions and to run the setup link; the service says it once in its log (`errOlderAgent`) and parks, before it touches the engine or VaultSync's copy — an exiting one would only be started again by launchd every 10 s (as in decision 053 (8)); `status` of such a build says it is older than the VaultSync set up here; `start` judges only a service that runs this very build; beside another build it says so and leaves whether that one syncs to `status`, which asks the running agent (a verdict from this program's own pin was wrong both ways, and waiting for the other build's agent was wrong for a slow one). An older build writes nothing, not even decision 053 (8)'s park note (it would drop a newer one's fields), and its service ends when its program is replaced — the setup link putting the current app in place, or one dragged over it — so launchd starts the current build; a run in a terminal says why it ended. A pin only ever moves forward. `agent.json` moves from format 1 to format 2 (format 1's fields) where a build from desktop-v0.2.0 on takes over — its setup once its copy is in place, an engine it installs (a run only once it holds the engine lock: one refused there has taken over nothing), or VaultSync for Mac's run or uninstall keeping the copy at its build; every other write keeps format 1, so a desktop-v0.1.0 still installed keeps running beside a later `pair` or `run`, and writes any other format as its own, so a later format reaches agent.json with that build's first write. The agent reads the format before the rest, so a newer one is never taken for damage. desktop-v0.1.0, which has none of this guard, refuses every format but 1 and so neither sets up nor runs where a later VaultSync took over. A release that adds a field an older build must not drop raises the format too.

**Why.** Syncthing does not promise to read state a newer version wrote; an older engine may refuse it or run on it unchecked, and the agent cannot tell which. Stopping fails to "nothing syncs", which the other devices show and the setup link undoes. The guard protects only from the build that carries it on, so it ships in the first release with the app.

**Rejected alternatives.** Installing the older pin as before (the hazard). Raising the format only with the first pin bump past v2.1.6: a step a bump can forget, and until then a kept v0.1.0 would still move the service beside the app (decision 053). Running the newer installed engine from the older agent: the agent edits the engine's config in the shape its own pin generates, and that shape may differ (#267 keeps the installed engine only in the other direction, a newer agent whose pin could not be downloaded).

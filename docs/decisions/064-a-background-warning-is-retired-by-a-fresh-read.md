# 064 — A background "no vaults" warning is retired by a fresh read of the running engine, in memory only

**Context.** A background run that finds no vaults records `.noFoldersConfigured`, and `backgroundSyncIssueItem()` surfaced that outcome until the next background run replaced it. A run before the first share was accepted — right after Hub pairing — left "Background Sync Found No Vaults" and "Action Needed" above an up-to-date vault for good (#210). The run's folder wait also gave one answer for three states: a running engine with no folders, a stopped engine (the bridge answers `[]`), and a list that could not be read.

**Decision.** (1) The foreground retires the warning when a read of the bridge — the poll's or `refreshFolders`' — shows it to be over: the outcome is `.noFoldersConfigured`, one engine ran across the read (`eventStreamGeneration()` non-zero and equal before and after it), the list holds a vault, and the read began after this process first held the outcome, both times on the monotonic clock (`SyncthingManager.freshFolderReadResolves`). The outcome was recorded before it was held, so the read is newer than the run, and a wall clock set back cannot keep the two apart. The retired outcome is kept in memory and matched by value; any newer outcome surfaces again. (2) Nothing else changes: the persisted outcome, its Activity entry, the last-sync data and the background completion's widget tier stay as the run wrote them; the issue floor never held this kind (013). (3) The background run classifies its last read as configured, verified empty, engine stopped or unreadable (`BackgroundSyncService.folderAvailability`). Every state but configured still records `.noFoldersConfigured`; the detail and the trace say which it was, and the remediation holds for all three ("if this iPhone has no vault yet, accept or create one; if your vaults are there, open VaultSync"). Only an engine that is down after a read ends the wait early; one restarted during the read is read again. The 3-second window stays: `StartSyncthing` loads the configuration under the bridge lock before it reports the engine as running, so a running engine's empty list is its configuration, not a start-up gap — the window was not the cause.

**Why.** A warning about the past must end when the present is proven different, and only a read of the running engine proves it. The header and the widget follow the issue list (012), so retiring it there is the one place that moves every surface.

**Rejected alternatives.** *Comparing the read with the outcome's wall-clock timestamp:* a clock set back after the run would hold the warning up again. *Retiring it whenever `folders` is non-empty:* the list is a cache — it survives a newer no-vaults outcome and would hide it at once. *Persisting the resolution:* a new stored format for a state the first poll after a launch re-establishes within seconds; after a relaunch the warning shows until that read, which is true until it happens. *New `SyncResult` values for a stopped engine or an unreadable list:* changes the persisted outcome's format and the completion's severity; the detail carries the difference instead. *A longer or shorter folder wait:* the window was not the cause (see 3); #210 leaves it as it was. *Retiring the other background warnings (timed out, could not start) from foreground state too:* each needs its own proof of being over and is not this issue.

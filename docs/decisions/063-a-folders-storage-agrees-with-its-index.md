# 063 — A folder's storage is the directory that agrees with its index; the marker alone is no proof

**Context.** 003 made the `.stfolder` marker the proof that a directory is a folder's own: `SetFolderPath` moved a folder whose directory is gone to `<selected folder>/<its path>` when the directory there held the folder's marker file. A copy made by hand carries that marker (#315, seen on a device: a copy made in the Files app keeps `.stfolder` and `.stignore`). A vault copied under another folder, the first folder deleted later, the other one selected: the folder was continued in the copy, and its first scan there sent out what had synced since the copy was made, as deletions and as the old versions. `TestIssue315_ACopyWithTheFoldersMarkerIsNotItsStorage` shows it on a real peer.

**Decision.** (1) The marker stays necessary and is no longer sufficient. `SetFolderPath` also requires that the directory agrees with what this device recorded for the folder (`verifyFolderStorage`): every entry of the local index is there with its kind, size and modification time, and every entry recorded as deleted is absent — read with the scanner's own comparison, through the folder's own view of a filesystem. Ignored entries are skipped. Two differences take nothing away and pass: a file the index has never seen, and a file whose time alone differs and whose content, read block by block, is the recorded one — what a restore from a backup can leave of every file. An entry the index marks for a rescan, an entry that cannot be read and an index that cannot be read to its end are refusals (039). (2) The bridge refuses while the folder's own directory exists: a live folder is never re-pointed (003), and its index moves with every file that arrives, so nothing compared against it would still hold. (3) A refusal leaves the folder where it is. The app tells this one from the others by the bridge's own text (`FolderStorageMismatchError`), and the vault's card says that a folder of the vault's name was found, that it does not hold what this iPhone last synced, and the way on: remove the vault and accept its share again, which asks before it combines (002, 007).

**Why.** Re-pointing is destructive for one reason: the folder goes on with its index, and the scan takes every difference for a change made on this device. So the proof is that there is no such difference. It needs no new state, and it holds for exactly the directories the repair exists for: the one the folder was last scanned in, moved as a whole or under a container whose path changed (#25). A copy passes only for as long as nothing has synced since it was made, and going on in it then changes nothing on any device.

**What it costs.** A vault changed since its last scan — a note edited, renamed or deleted in Obsidian while VaultSync was not running — is refused after a move as well: by its content, such a change cannot be told from an older copy. That vault gets the card where the repair used to be silent, and accepting it again keeps both sides. Notes that are only new do not have this effect.

**Rejected alternatives.** *Letting a differing file pass when it is newer than the index says:* a copy made with another tool carries the time of the copy, and a note edited on another device before that time and synced after it then looks older than its own stale copy. *Recognising the directory itself*, by the file number of its marker, recorded while the folder is alive: it would survive edits, but not a restore or a migration, which create every file anew, and it is state that goes stale — after a vault is removed and accepted again elsewhere, the record would vouch for the directory it left behind. It can stand beside this proof, never in its place. *Reading the content of every file that differs, to tell which side is older:* content shows that two versions differ, not which came first; it settles only the case above, where it shows that nothing differs. *Going on in the copy with the folder paused, for the user to decide there:* the folder would already be re-pointed (003).

**Not covered.** A copy the user puts in the folder's own place, under its own path: to the engine that is the folder, changed by hand, as on every Syncthing device. An index without entries agrees with every directory; all a scan finds there is new.

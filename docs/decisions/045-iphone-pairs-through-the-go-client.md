# 045 — The iPhone pairs with a Hub through the Go client; the QR link format

**Context.** M2 (#174): VaultSync on iPhone joins a Hub by its code or a QR code. Pairing protocol v1 (decision 036) had one client, in the Hub's `package main`, which nothing else could import.

**Decision.** The device half of the protocol lives in the importable package `hub/pairing` — wire types, AES-GCM boxes, the client, the code word list with `NormalizeCode`, the discovery client and the link builder. The Hub's server half (sessions, rate limits, failure counting, provisioning guards) stays in the command and only gained type aliases. `go/` links the package through `replace github.com/psimaker/vaultsync/hub => ../hub`; `go/bridge/hubpairing.go` exposes it to Swift as calls bound to one pairing flow, answered with versioned JSON envelopes. The QR link is `vaultsync://pair?code=<CANONICAL-CODE>[&hub=<IP>:<PORT>]`, form-encoded and built only by `pairing.Link`; `hub` is a hint that skips the search. The app keeps five rules: every address that reaches a socket is a private, loopback or link-local IP literal — checked when a link is parsed and again at dial time, the Hub's own rule for its callers; a link only prefills, pairing takes a tap; a code goes only to the Hub the user chose, never to every Hub that answered; provisioning asks the Hub to share and the existing pending-share flow accepts (decisions 001, 007, 008); a provision whose outcome is unknown is never retried.

**Why.** One SPAKE2, one word list and one normalization for the Hub, its CLI and the iPhone: a Swift copy is a second place for a transcript or encoding bug, and every mismatch costs the user a wrong-code attempt. The link is the one text the Hub and the app must agree on, so the Go builder and the Swift parser are tested against the same golden strings, and the address rule is the Go floor itself.

**Rejected alternatives.** SPAKE2 and the word list reimplemented in Swift (two implementations to audit and keep in step). Moving the server into the package so the bridge test can run it in-process (refactors security-relevant server code for a test; the bridge test runs the real `vaultsync-hub` binary against a fake Syncthing instead). Host names in `hub=` (needs DNS and address pinning; the Hub prints IP literals). Trying the code on every Hub that answered, as the CLI does (each try is a counted wrong code on someone else's Hub). "Upload this iPhone's vault as new" from the canvas (the unchanged `create` shares a same-named vault instead of creating one, so "new" cannot be promised; deferred until the protocol has an atomic create-only step).

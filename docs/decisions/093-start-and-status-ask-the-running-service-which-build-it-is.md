# 093 — `vaultsync start` and `status` ask the running service which build it is

**Context.** `vaultsync start` says "already running" or "running again" only where the background service runs this very build. Where this build is older than the VaultSync set up here, it says the service does not sync, because a service of this build parks (decision 054). Beside another build it says only that another build runs, and that `vaultsync status` says whether it syncs. `status` names `vaultsync stop`, then `vaultsync start`, as what installs this build's pin only where the service runs this build (decision 078). Both judged this by two files: this program, read at the path it runs from, and the program the service names, compared byte for byte or by their code directory (`sameBuild`). A file can be replaced while the program started from it runs on (#416):
- In the instant between a `vaultsync` process's start and its read of itself, a newer VaultSync for Mac's run puts its own build in the copy's place as it comes up. An older copy then took the newer service for itself and said it does not sync, while the newer service synced. #415 (`0f91f5d`) left only this instant.
- A service whose run lives on after its program was replaced, which `start` leaves alone since decision 085, was called this build, "already running". The program may be VaultSync's own copy, replaced outside setup's own restart, which no watch ends. Or it may be VaultSync for Mac, in the seconds before its run's watch sees the replacement (decision 053 (7)).

Neither case changes data. Only the words were wrong. But "does not sync" said of a service that syncs is the claim a person may delete files on, and those deletions reach every device.

**What a build carries.** This was read from the desktop-v0.3.0 assets (the bare `vaultsync_darwin_arm64`, the app's agent, `vaultsync_linux_amd64`) and from the rc.1 asset, with `go version -m` and `go tool buildid` (Go 1.26.11). Two local builds were made with the release job's flags and stamped 0.4.0 and 0.4.1, and one plain `go build`.
- **Build information names no release.** The release job builds with `-trimpath -buildvcs=false -ldflags="-s -w -X main.version=…"`. `-trimpath` keeps `-ldflags`, and with it the version, out of the build information. `-buildvcs=false` keeps the commit out. The main module reads `(devel)`, and so does the hub module (`=> ../hub`). The 0.4.0 and 0.4.1 builds read the same, apart from the file's path.
- **The version cannot be read from the file.** It is only in `main.version`, and a stripped asset has no symbol table to find it by (`go tool nm` lists imports only).
- **The Go build ID tells releases apart** (0.3.0 from its rc.1, 0.4.0 from 0.4.1). It is the same for the bare agent and the app's agent of one release, which are signed apart and differ in their bytes. But a running program has no way to read its own build ID from memory.
- **A plain `go build` carries `vcs.revision`, `vcs.time` and `vcs.modified`.** A pull request's build is stamped `dev-<commit>` without them. A test binary carries neither.

**Decision.**
1. **What one build is.** For what `start` and `status` say, two programs are one build when they carry the same build mark. The mark is compiled in, and a program reads its own from memory, never from the file at its path (`buildMarkOf`, `buildMark`). It is the version the build was stamped with (`-X main.version`): a release, a release candidate, or a pull request's `dev-<commit>`. A build stamped with none gets `dev+<vcs.revision>`, where a clean checkout built it (`vcs.modified=false`). Every other build has no mark and is one build with nothing; so is a mark that cannot travel as a header value. One release is one build on either architecture: what `start` and `status` decide rests on its pin and its `agent.json` format. `sameBuild` stays for setup's choice of which program the service runs (decision 053), which is a question about files.
2. **The running agent says its build.** Every answer of the control socket carries the header `VaultSync-Build` with the agent's mark (`control.BuildHeader`). That includes the 404 that `start`'s wait asks for (decision 085), errors, and `/v1/status`. A build without a mark sends none. Nothing in the answers' JSON changes, and nothing is persisted. Readers older than this ignore the header.
3. **Which build runs is what the agent's answer says** (`runningBuildOf`):
   - An answer with this program's mark comes from this build.
   - An answer with another mark comes from another build. So does an answer without a mark, where this program has one: every build from this release on says its mark on every answer, so one that sends none is an earlier build.
   - Where neither has a mark, which build runs is not known.
   - Without an answer it is not known either. A parked run serves no socket, and a run on its way up has not answered yet.
4. **What `start` says.**
   - Beside this build: "already running" where it left the run alone, otherwise "running again". Where this vaultsync is older than what is set up, a note follows: this VaultSync is older (both versions named), and the setup link gets the current one. Before, this case was the refusal "runs, but it does not sync". An answering run of this build passed its own check at its start, so it runs; it parks only at its next start (decision 054). "Does not sync" was the riskier claim of the two.
   - Beside another build, also unchanged: "✓ The background service is running. It runs another VaultSync build than this vaultsync — vaultsync status says whether it syncs.", with the note where this vaultsync is older than what is set up. A running service whose program was replaced is left alone (decision 085) and gets these words. `start` adds no "stop, then start": beside a newer service, which an older download's `start` meets, that would lead nowhere.
   - Answered, with no build known: "✓ The background service is running. vaultsync status says whether it syncs."
   - Without an answer, `start` names no build. It says, as decision 085 does, that the service does not answer yet and may still be installing its sync engine. What follows is a way that ends: `vaultsync status` says what the service does; if it stays so, `vaultsync stop`, then `vaultsync start`; and where that changes nothing, the setup link, which brings the current VaultSync to the service (decision 054). Stop and start alone would loop beside a service of an older build: it parks and never answers, and a start runs the same program again.
   - Without an answer, where this vaultsync is older than what is set up, `start` refuses (exit 1) without claiming which build runs: the service does not answer, this VaultSync is older (both versions named), a background service of this build does not sync, run the setup link, and `vaultsync status` says whether the service syncs. A service of this build parks and never answers, so only these words hold whichever build runs. A newer service that is slow to answer gets the same refusal; that is by design, since the words hold for it too and status tells.
   - What is set up is read after the wait for an answer, since a newer run records its engine as it comes up. One wait lasts up to about 20 s: 39 quick looks, then one ask that gets no answer in its time (decision 085). Where a run left alone is gone by then, `start` loads it afresh and waits once more, so up to about 40 s.
   - Nothing in `start` reads a program's file for this any more (`serviceRunsThisBuild` is gone).
5. **What `status` says.** Where a kept older engine runs (decision 078), `status` asks the agent once, the same ask `start` makes, at most 3 s and ending with `status`'s own context. Where the agent says it is this build, `status` names `vaultsync stop`, then `vaultsync start`, as before. Otherwise, no answer included, it says that `vaultsync setup` installs the pin, which holds in every case.
6. **What an older build's refusal says** (`olderRefusal`, decision 091). `pair`, `uninstall`, `pause` and `resume` of a build older than what is set up refuse. Whether the background service runs this build, which then parks, no look tells: a parked run never answers, and the files at the programs' paths may have been replaced since the programs started. So the refusal claims neither. It always names the program that holds the VaultSync set up here, or the setup link where none is found. `uninstall` and `pause` name `stop` wherever a service is installed. Where the program named is not the one the service starts, or none is named, `pair`, `pause` and `resume` add what holds if the service runs this build: "Where the background service runs this VaultSync too, nothing syncs until the setup link brings the current one to it." Before, a file look decided whether to say "Nothing syncs here meanwhile: the background service runs this VaultSync too."
7. **The tests** give every app and every fake agent this build's mark unless a test says otherwise (`defaultBuildMark`); a test of another build sets the app's or the agent's `build`, and one of a build without a mark sets `noBuildMark`. A test written without marks in mind then behaves as the program does.

This changes decision 054's sentence that `start` judges only a service that runs this very build: it still does, but by the service's answer, and without one `start` names no build. It changes decision 085 point 3's third bullet: without an answer, `start` no longer says that another build runs. It changes decision 091 point 3's bullet on a service that runs this very build: the refusal no longer judges that (point 6).

**Why.**
- Only the running program knows which build it is. The file at its path says which build the next start runs, and only while nobody replaces it.
- An answer from the service is what decision 085 already waits for, so the build costs no extra ask.
- Every claim `start` now makes about the build holds whatever happened to the files. The one that can lead to lost notes, "does not sync", is no longer made of a service whose build `start` does not know.

**Rejected alternatives.**
- *Build information read from memory (`debug.ReadBuildInfo`) against the service program's (`debug/buildinfo`).* A release's build information names no release (above).
- *Stamping it there, by building releases with `-buildvcs`.* That changes the signing workflow, and a release candidate and its release from one commit would read the same. Released builds carry nothing either way.
- *Reading this program's own running image.* `/proc/self/exe` gives it exactly, but only on Linux. On macOS, `csops` and `proc_pidinfo` are libc calls the agent has no wrapper for: it is built with `CGO_ENABLED=0`. Opening its own file earlier only narrows the instant.
- *The Go build ID.* A file has one, but a running program has no way to read its own.
- *Keeping the file look where no agent answers.* That keeps the instant, and with it the claim "does not sync".
- *Running the service's program (`vaultsync version`)* to learn its release, as the setup link does (decision 080). `start` and `status` would run a program to learn what the running agent can say.
- *A field in `/v1/status` only.* `start` waits on `/v1/`, not on `/v1/status`, which asks the engine first (decision 085).
- *The locks as evidence for the older case* (the engine lock, the Syncthing home lock and `setup.lock` all free after the wait). That means more looks, and it would depend on `run`'s order of locks beyond what decision 085 pins. The words above need none of it.
- *Restarting a running service whose program was replaced.* A living run is left alone (decision 085). Its run is a build that passed its own guards when it started.

**Not covered.**
- Builds before this one judge by files as before, and send no mark: beside them, a build from this release on says that another build runs.
- A `vaultsync run` in a terminal answers on the socket like the service's run, and its build is taken for the service's (as in decision 085).
- On a Mac, the old run of a replaced VaultSync for Mac may answer while its watch has not yet ended it. `start` then says that another build runs, which is true at that moment. launchd starts the new one seconds later.
- setup still reads this program by its path, in `refuseBesideAnotherBuild` and `installAgentCopy`, and so does the older refusal's search for the program set up here (`setUpProgram`), which passes over this program's own file (#281).
- A version stamped by hand on changed code is taken for that release: two programs stamped alike are one build. No release asset is affected, since one tag stamps one version for every target.
- `status` does not name the build the service runs.

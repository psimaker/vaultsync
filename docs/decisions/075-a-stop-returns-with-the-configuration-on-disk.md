# 075 — A stop returns with the configuration on disk

**Context.** The app stops the sync engine at the end of a background run and in the forced restart after a silent push; after a background run's stop the run completes its task, and iOS can suspend the process at once. The engine's configuration wrapper writes `config.xml` on a five-second timer and once more as its `Serve` loop returns. `StopSyncthing` canceled the early supervisor that runs it and returned, so the last change reached the file 10 to 12 ms after the stop had ended (measured on a Mac, 10 of 10 rounds, #302). A start right after a stop could load the file without that change, and bridge tests slept or polled for the write.

**Decision.** (1) `StopSyncthing` returns only once the early supervisor has stopped its services, the configuration wrapper's last save among them: after `App.Stop`, the database and the cancel, `stopEngineLocked` receives from the channel `ServeBackground` returned (`stEarlyDone`). (2) One bounded wait covers all of it (`lifecycleTimeouts.stop`, 30 s; decision 038). A stop that overruns finishes in the background, and `stStopPending` closes only after its save, so the next start waits for it. (3) The channel receives once, and `release` is its only receiver, on every path; a stop without an engine instance takes the same bounded path. (4) Tests rely on it: a test that restarts the engine reads `config.xml` right after the stop, with no sleep or poll in between (`TestIssue302_…`, and the #185, #315 and rescan migration tests).

**Why.** A stop that returns before the write leaves the last change only in the memory of a process that iOS may suspend or end next, and hands a start that follows at once a file without it. The supervisor's return is the completion signal that has a bound: suture stops each service within its stop timeout (`svcutil.ServiceTimeout`, 10 s) and returns after it. That bound is also the guarantee's limit: a write that itself takes longer than 10 s is not waited for, and the stop then returns as it did before this decision.

**Rejected alternatives.** *A completion signal from the wrapper itself.* The wrapper's `Save` closes the file and then logs `ConfigSaved` through the event logger, which the same supervisor is stopping. If that send blocked, a wait for the wrapper's own return would never end: `stStopPending` would never close, and every later start would be refused until the app restarts. *A longer stop deadline* to cover `App.Stop`'s upstream bound (about 20 s) plus suture's 10 s. The app's wait for a background stop (`SyncthingManager.start`, 35 s) mirrors the bridge's deadline and would have to move with it. Both worst cases in one stop end in the overrun path of (2).

**Not covered.** A change made while the engine runs reaches the file on the five-second timer, and an app closed in the app switcher within those seconds loses it. That case stays with #151's configuration-durability item, and #316's texts ask people to wait ten seconds; saving in every commit is not rejected here. `StartSyncthing`'s error paths cancel the early services without waiting: the wrapper then holds only the start's own settings and migrations, which are idempotent and written again by every start.

# 057 — The menu's Start runs what the service runs, in a process group of its own

**Context.** The menu-bar app offers Start VaultSync when no agent answers (#248, decision 050). `vaultsync start` says whether the service syncs by comparing itself with the program the service runs, and a person who only uses the menu sees what it says. On a Mac the tray is itself a login job.

**Decision.** (1) Start runs the program the background service runs: the one its LaunchAgent names on a Mac, VaultSync's own copy on Linux, the only one setup gives the unit. Without a `vaultsync` named or there, VaultSync's copy, whose start says what is wrong. Never one found on `PATH`. It runs `start --state-dir` with the menu's own VaultSync folder (#290): the program inherits the menu's environment, and on Linux a menu started with `--state-dir` in a session whose `XDG_STATE_HOME` names another place made start read another `agent.json` than the menu and the service. `start` takes that flag and refuses any other argument; desktop-v0.2.0 and v0.3.0 ignore every argument after `start`, so beside them the menu's start is what it was. With neither program there and runnable, the menu offers no Start and says that VaultSync's program cannot be started, with the setup link: a start cannot help where the program is gone or cannot be run, and the `vaultsync` command may be gone with it (#290). (2) It runs in a process group of its own, with its own time limit, not the menu's context. (3) After it says the service runs, the menu asks the agent a fixed number of times over about 15 s of waiting in all, the Start item disabled. An ask that gets no answer in its time ends them early: something is there that takes a request and says nothing, and another ask would only make the wait as long again. What the start came to is settled once, by the first look from the end of the asks on that tells: one that finds nobody makes the menu say, with a notification, that the service does not answer, and one that finds an answer says nothing, since that agent speaks for itself. A look that tells neither (no answer in time, a connection dropped, an answer cut short) leaves it to the next. What start said goes as soon as an agent answers, well or badly, in the wait or after it; a look that reaches no agent, or gets no answer in time, takes nothing back. (4) The menu's asks for the agent's status run beside its loop (#290), one at a time: an agent slow to answer, as its engine is right after a start, held every click behind each ask; no click waits for one now. A click on Pause still waits for its own request on the loop (up to 15 s), and the clicks after it with it. Whatever asks for a look while one is out — a poll, the menu opening, a pause, a pairing's end, the wait above — is one more ask once that one is answered. Start and Pair act only on the answer to an ask begun after the click, as they did when the menu asked on its loop; answers to asks begun before a pause's request returned are not shown, so the Pause item never offers what was just done. The one-instance lock is taken as each ask begins. (5) *(2026-11-27, #291)* The menu notifies:
- a refusal of start, as before, and a note start adds after it worked (a line that begins `Note:`);
- every end of a pairing that no dialog showed: the time limit, a question that could not be shown, a closing message that could not be shown;
- a pause's answer and an open's failure, as before.

A notice and its notification are set in the menu's loop only: a start, an open and a pairing hand their outcome to it through their one channel each. A pairing's end and a pause's answer are the agent's words, and a look that finds no agent takes them back; start's keep (3), and an open's failure, the desktop's, stays.

A notice, and the line under the headline, are shown on at most four lines of at most 60 characters. They are broken at spaces and never inside a character; a word longer than a line is broken where it must. Where more was said, the middle goes: the first lines, the last of them ending in "…", and the longest end that fits, from the start of a sentence or a clause. Every line's tooltip then holds the whole text. A notification carries the whole text on one line, cleaned as a dialog program's failure is (055), at most 400 characters.

**Why.** Only the program the service runs can speak for it. When launchd ends a login job it signals what is left in that job's process group, so a Quit could kill a `launchctl` half-way and leave the service unloaded with nobody told; a stand-in login job showed the signal arrive and, with its own group, not arrive. A run that keeps ending before its socket counts as running for a moment each time, so "running again" alone would stand under "not running"; and a run can end right after its first answer, so a first answer settles nothing. A menu item is one line (5): macOS cut a long notice in its middle, where the remedy stood, and widened the menu to three quarters of the screen for it; a cause comes first and its remedy last, so the end is what stays. A person who clicked Pair a Vault… and saw no dialog learned of its end only by opening the menu again. A notification leaves the app for the system's notification service.

**Rejected alternatives.** The agent beside the app, then the copy: "beside the app" is only a folder named `MacOS`, so a bundle kept in Downloads spoke for the service. The copy, then the agent beside the app: the run replaces the copy while start still compares with it, so an old copy can say a newer service does not sync; a stale or damaged copy also hides the older-build refusal and its remedy. `PATH`: an old download or anything of that name, with no terminal to show which ran. Quit waiting for the start: up to two minutes of an app that seems stuck. Ending the wait at the first answer: three review rounds of conditions for what counts as one, each leaving a run that dies just after it unsaid. Ending the wait by the clock: whether the last ask was still made then depended on how long the ones before it had taken. Taking the folder for start from the service's unit file instead of the menu: it would also cover a terminal in another session, but changes where start takes its folder from for every caller, while only the menu was wrong. An ask per trigger, several at once: answers could come in any order, and an older one would be shown last. Shorter words alone (5): the agent's texts come from other builds too, and the longest it says after a start is 352 characters. The first four lines and a mark: the remedy is the part that went. A notification for every notice: an end a dialog showed has been read. A pairing's goroutine notifying the time limit itself, as before: what reaches the menu goes through the loop, whose state it is.

# 062 — A Hub's error text is one clean, short line, made in the pairing client

**Context.** When a pairing request fails, the pairing client hands out the text of the answer: `APIError.Body` for an answer with an error status, and `HubPayload.Error` for what a Hub reports inside its encrypted answer. `vaultsync-hub pair` and `vaultsync pair` print both, the menu shows the second program's words in a dialog, and the iPhone's bridge passes them to the app's log. The first text comes from whatever answered at the address that was dialled, before the key exchange; the second from a Hub that knows the code, and it passes on what that Hub's Syncthing said. Neither was cleaned or bounded (#319): a terminal sequence, U+202E, line breaks, up to the 64 KiB an answer may be.

**Decision.** (1) `errorText` in `hub/pairing` makes such a text one line: every run of white space — a line break, a tab and U+2028 included — becomes one space, what `SanitizeName` drops from a name is dropped (061), and the rest is cut to 300 bytes between two characters, with "…" at the end. (2) The client applies it to both texts before it hands them out, and reads the kind of a refusal from the cleaned text: what is judged is what is shown. (3) An error stays an error. An answer whose text has nothing to show reads as its HTTP status does, like an answer without a text; an encrypted answer's error becomes a fixed phrase, because callers tell a refusal from a share by whether `Error` is empty.

**Why.** In the client, so that no program that prints an error has to remember — the reason the Hub's name is cleaned there. A space for a line break, because two lines must stay two words: for the reader, and for the phrases `FailureKind` and `Handshake` look for ("rejected", "code has expired", "locked"). 300 bytes, because the longest text a Hub words itself is its own words in front of an answer of its Syncthing, which it cuts at 200 bytes: about 260 in all, and its refusals stay under 110. `TestIssue319_TheHubsOwnRefusalsArriveWhole` holds every refusal the server sends against what the client hands out, so a refusal reworded past the bound fails there. Nothing on the wire changes: Hubs and devices with and without this change pair with each other as before.

**Rejected alternatives.** Cleaning in each program that prints: three places today, and the next one forgets. Reading the kind from the text as it came and cleaning it only for display: two texts for one answer, and the kind would hang on words nobody sees. Dropping a line break as a name does: "wrong" and "attempts" on two lines would read as one word. Leaving the encrypted answer's error as it came because that Hub knows the code: the same programs print it, and the Hub passes on text it did not write. Cleaning on the Hub before it sends: the sender of an answer is the one party a device cannot rely on.

**Not covered.** A vault's label from a Hub (#320).

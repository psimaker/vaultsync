# 053 — On a Mac the service runs from VaultSync for Mac in Applications, and the menu-bar app opens at login

**Context.** M4 step 3 part 2 (#254, #176). After #252 (decision 052) the agent and `VaultSync for Mac.app` are signed and notarized, but the LaunchAgent still ran the agent's copy in VaultSync's folder — macOS listed it under the certificate's name and asked its permissions for that path — and the menu-bar app had to be started by hand.

**Decision.** (1) `setup` points the LaunchAgent at `VaultSync for Mac.app/Contents/MacOS/vaultsync` when it runs from that program and the bundle is installed: named so, directly in `/Applications` or `~/Applications`, `CFBundleIdentifier` `eu.vaultsync.desktop`, the menu-bar app a plain executable beside it (`findInstalledApp`). Anywhere else — a bare download, Downloads, a disk image, an App Translocation path — the service runs the copy as before. An existing service moves once: its plist changes, so it is booted out and loaded afresh. The last setup decides; one from the copy moves it back. (2) The plist names the app (`AssociatedBundleIdentifiers`), so Login Items shows "VaultSync for Mac". (3) A second LaunchAgent, `eu.vaultsync.tray`, starts the menu-bar app at login: `RunAtLoad`, `KeepAlive {SuccessfulExit: false}` (again after a crash, not after Quit), `ProcessType Interactive`, its own log. A second instance ends with 0, so it is not restarted every ten seconds. Setup kicks it only when a new agent came with the app; a failure to set it up is said, not fatal. (4) The copy in VaultSync's folder stays current: it records which agent the service last got (a new one restarts both jobs), and it is the way back when the app is gone. The command link follows the program the service runs; a link to anything that is not VaultSync's own stays. (5) `uninstall` removes the menu-bar app's job first and waits until launchd let go of it. `--remove-data`'s probe passes over a `tray.lock` held while that job runs, and still refuses one held by an app opened by hand. (6) The setup link installs the app on a Mac when the release's `SHA256SUMS` lists `VaultSync_darwin_<arch>.zip` — verified, unpacked, its identifier checked. It goes where an app of that name already is, else to `/Applications` when writable, else to `~/Applications`, and the setup runs from there; otherwise the bare agent is the installer, as before. It never replaces a bundle whose identifier is not `eu.vaultsync.desktop`, nor a link (doctrine 002).

**Why.** macOS keys Login Items, the local-network prompt's wording and a helper's permissions to the app around the program. A service outside the app keeps the developer's name and a path of its own. The app in Applications is the one place that survives a restart; a LaunchAgent pointing into Downloads or a translocated copy would lose its program.

**Rejected alternatives.** `SMAppService` (macOS 13+, needs Objective-C glue in the tray, and a login item is not restarted after a crash). A wrapper script in the plist that falls back to the copy (Login Items would name the shell, not the app). Pointing the service into any bundle setup runs from (a translocated path vanishes). Replacing an existing `VaultSync for Mac.app` without reading its identifier. Removing the copy once the service runs from the app (no record of the installed agent, no way back without the app).

# 053 — On a Mac the service runs from VaultSync for Mac in Applications, and the menu-bar app opens at login

**Context.** M4 step 3 part 2 (#254, #176). After #252 (decision 052) the agent and `VaultSync for Mac.app` are signed and notarized, but the LaunchAgent still ran the agent's copy in VaultSync's folder — macOS listed it under the certificate's name — and the menu-bar app had to be started by hand.

**Decision.** (1) `setup` points the LaunchAgent at `VaultSync for Mac.app/Contents/MacOS/vaultsync` when it runs from that program and the bundle is installed: named so, directly in `/Applications` or `~/Applications`, the bundle itself (no link), `CFBundleIdentifier` `eu.vaultsync.desktop`, no link inside it down to `Contents/MacOS`, the menu-bar app a plain executable beside it, and this account's — the bundle's own folders writable to it, not `/Applications` itself, which a standard account cannot change although it owns the app it put there (`checkApp`): another account's app is theirs to update or trash. Setup run from a VaultSync for Mac that does not count says so and why. Anywhere else — a bare download, Downloads, a disk image, an App Translocation path — the service runs the copy as before. An existing service moves once (its plist changes: bootout, bootstrap); setup from the copy takes it back into the app only as (4) says. (2) The plist of a service that runs the app's agent names the app (`AssociatedBundleIdentifiers`), so Login Items and local-network privacy can attribute it to "VaultSync for Mac" (same team; TN3179); the copy's names none, also with the app installed — it is not the app's, and the app's trip to the Trash does not stop it. (3) A second LaunchAgent, `eu.vaultsync.tray`, starts the menu-bar app at login: `RunAtLoad`, `KeepAlive {SuccessfulExit: false}` (again after a crash, not after Quit), `ProcessType Interactive`, its own log; a second instance ends with 0. It exists only for a service that runs from the app: setup removes it when the service runs the copy, and any setup removes one whose program is gone. Setup restarts it only when its program is not the one it was last started with (4), never enables a job the person disabled, and says rather than fails when it cannot set it up. A loaded definition whose program differs from its file (a reload that failed) is loaded afresh, not just restarted. (4) The copy is refreshed in setup once the engine is in place — never a build whose engine a failed download left out, since without the app the service runs it — and by a service started from the app and by `uninstall` run from it (an app updated in the Finder had no setup): it is the way back without the app, which must not run an older build (#264). `agent.json` records (`started`) the SHA-256 of the programs the service and the tray job were last started with, written once they run; setup restarts a job whose program differs — also when an earlier setup stopped between the copy and the restart — and no record restarts once. When the app is gone, `status` and `start` (run from the copy) say so and name the way back; setup from the copy removes a start at login whose app is gone; `uninstall` points the command link back at the copy as soon as the service is gone. With an app that counts installed, the service runs from it: setup from another program of the same build — the copy, or the bare agent of the release, which is signed apart (same code directory, other bytes) — puts the service into the app; another build stops before anything changes and says to update the app — it never takes the service onto the copy beside it. A copy that cannot be brought to the app's build keeps the command on the app. (5) `uninstall` removes the tray job first and waits; `--remove-data` passes over a `tray.lock` held while that job runs and looks again once it is gone. (6) The setup link installs the app when the release's `SHA256SUMS` lists `VaultSync_darwin_<arch>.zip`: verified, unpacked in a folder of its own beside its place (putting it there is a rename, never a copy), its identifier read from the top of its Info.plist, refused unless the agent would take it (an XML Info.plist, both programs plain executables), its agent run once, then moved where VaultSync for Mac is and this account can replace it, else `/Applications` if writable, else `~/Applications`; an app of this account's that it cannot replace (in a folder only an administrator may change, or locked) stops the setup with the reason instead of a second app beside it; the setup link never runs as root (every check of whose an app is would pass); the same build is not replaced, the old one is set aside in a new folder beside it, and a move that stops (an interrupt, a second signal during the restore) is undone and the old one put back — only into an empty place, else named where it is; something put at the place meanwhile (another setup) is left as it is. Never replaced: another identifier, a link (doctrine 002). A person who wants only the icon off at login uses `launchctl disable`, which setup respects. (7) A service started from the app — also a `vaultsync run` started through the command link into it — looks from its first moment, by the path it was started with (so no look at the bundle can keep it from being watched), and then every 5 s whether its program is still there; anything but the program there (no access, a file where the bundle was) counts as missing; missing at two looks 2 s apart (an update leaves the place empty for an instant) — moved, or in the Trash, which leaves a running program running until the next login — it stops the engine and ends (`errAppGone`, said in the service log); launchd parks the job until the program is back and then starts it by itself.

**Why.** The app in Applications is the one place that survives a restart, and Apple's model (`SMAppService`) ties an app's background work to its bundle: the person who moves the app to the Trash stops VaultSync.

**Rejected alternatives.** Service on the copy, only the tray in the bundle (review of #260): a service that outlives the trashed app keeps syncing, and deletions made in the belief that sync is gone reach every device — the service in the app fails to "nothing syncs", which the other devices show. The copy as the record of what the service runs (review of #260): a setup that stopped after refreshing it left the old build running for good. `SMAppService` (macOS 13+, Objective-C glue in the tray, no restart after a crash). A wrapper script in the plist (Login Items would name the shell). Any bundle setup runs from (a translocated path vanishes). Replacing an app of that name unread (it may be the person's own).

**Links.** #254, PR #260, #176, #222, #248; decisions 002, 048, 051, 052 (its (5) expected the bundle's `NSLocalNetworkUsageDescription` to serve the agent; an ad hoc build showed the system's text — the rc before desktop-v0.2.0 checks the signed one).

# 053 — On a Mac the service runs from VaultSync for Mac in Applications, and the menu-bar app opens at login

**Context.** M4 step 3 part 2 (#254, #176). After #252 (decision 052) the agent and `VaultSync for Mac.app` are signed and notarized, but the LaunchAgent still ran the agent's copy in VaultSync's folder — macOS listed it under the certificate's name — and the menu-bar app had to be started by hand.

**Decision.** (1) `setup` points the LaunchAgent at `VaultSync for Mac.app/Contents/MacOS/vaultsync` when it runs from that program and the bundle is installed: named so, directly in `/Applications` or `~/Applications`, `CFBundleIdentifier` `eu.vaultsync.desktop`, the menu-bar app a plain executable beside it (`findInstalledApp`). Anywhere else — a bare download, Downloads, a disk image, an App Translocation path — the service runs the copy as before. An existing service moves once (its plist changes: bootout, bootstrap); the last setup decides, one from the copy moves it back. (2) The plist names the app (`AssociatedBundleIdentifiers`, also on the copy's), so Login Items and local-network privacy can attribute it to "VaultSync for Mac" (same team; TN3179). (3) A second LaunchAgent, `eu.vaultsync.tray`, starts the menu-bar app at login: `RunAtLoad`, `KeepAlive {SuccessfulExit: false}` (again after a crash, not after Quit), `ProcessType Interactive`, its own log; a second instance ends with 0. Setup restarts it only when a new agent came with the app, never enables a job the person disabled, and says rather than fails when it cannot set it up. (4) The copy is refreshed first thing in setup; it records which agent the service last got and is the way back without the app. When the app is gone, `status` and `start` (run from the copy) say so and name the way back; setup from the copy removes a start at login whose app is gone; `uninstall` points the command link back at the copy as soon as the service is gone. Setup run from the copy while VaultSync for Mac in Applications holds the same agent puts the service back into the app; a different agent decides for itself. (5) `uninstall` removes the tray job first and waits; `--remove-data` passes over a `tray.lock` held while that job runs and looks again once it is gone. (6) The setup link installs the app when the release's `SHA256SUMS` lists `VaultSync_darwin_<arch>.zip`: verified, its identifier read from the top of its Info.plist, its agent run once, then moved where VaultSync for Mac is and this account can replace it, else `/Applications` if writable, else `~/Applications`; the same build is not replaced, the old one is set aside beside itself, and a move that stops halfway (a failed copy across disks, an interrupt) is removed and the old one put back. Never replaced: another identifier, a link (doctrine 002). A person who wants only the icon off at login uses `launchctl disable`, which setup respects.

**Why.** The app in Applications is the one place that survives a restart, and Apple's model (`SMAppService`) ties an app's background work to its bundle: the person who moves the app to the Trash stops VaultSync.

**Rejected alternatives.** Service on the copy, only the tray in the bundle (review of #260): a service that outlives the trashed app keeps syncing, and deletions made in the belief that sync is gone reach every device — the service in the app fails to "nothing syncs", which the other devices show. `SMAppService` (macOS 13+, Objective-C glue in the tray, no restart after a crash). A wrapper script in the plist (Login Items would name the shell). Any bundle setup runs from (a translocated path vanishes). Replacing an app of that name unread (it may be the person's own).

**Links.** #254, PR #260, #176, #222, #248; decisions 002, 048, 051, 052 (its (5) expected the bundle's `NSLocalNetworkUsageDescription` to serve the agent; an ad hoc build showed the system's text — the rc before desktop-v0.2.0 checks the signed one).

# 051 — Locks in VaultSync's folder: never through a link, probed without making a file, one more look before giving up to a holder

**Context.** The desktop agent, `vaultsync pair`/`setup` and the menu-bar app each hold a flock file in VaultSync's folder (`agent.lock`, `pair.lock`, `setup.lock`, `tray.lock`; `desktop/internal/lock`). `uninstall --remove-data` must refuse while any is held, and the review of #246 found three ways the locks themselves did harm.

**Decision.** (1) A lock file is opened with `O_NOFOLLOW`: a link in its place is an error, never followed — nothing outside the folder is opened, locked or made (a lock's open creates its file). (2) Before the uninstall asks anything or removes the service it probes every own lock with `lock.Probe`, which makes no file (a missing lock file is a lock nobody holds), and looks at the locks before it judges the folder, so a setup in progress (which holds `setup.lock` before it writes `agent.json`) is named rather than the folder handed over to be removed by hand; a refusal then costs nothing. A running service holds the engine's lock for as long as it runs, so that lock's held verdict is passed over then (its error is not); a held engine-side lock is named as the service (starting, pairing, on its way down, or one the service manager could not be asked about) or a terminal run, pair or setup, with the way out for each. (3) flock has no non-taking test, so the probe holds each lock for an instant; `tray.TakeLock` gives a held lock one more look after a moment before calling it another instance. (4) The removal holds every lock through the whole removal and takes the lock files away last: a `pair` or `setup` starting meanwhile meets a held lock and stops, the menu-bar app's second look finds `agent.json` gone (it goes first) and holds nothing; a `run` started by hand that was set up when it began waits on the held lock without making the folder, and refuses once `agent.json` is gone, leaving no file; only a run that began without `agent.json` sets VaultSync up afresh. The one instant left is between the lock files' removal and the folder's: lock files found alone then get a moment and are then taken, not looked at: taken, they are leftovers of owners that did not get to remove them and go under the removal's own flock, so no owner opening one in between is left with a lock on nothing; still held after one more wait, a tray.lock is the menu-bar app that stayed (a failure that names it), any other lock is VaultSync started again (reported as that, never as someone's files).

**Why.** (1) The locks are taken before the removal's own link check runs, and a lock's open makes its file. (2) A refusal after the service is gone costs the person their service and a second run with both questions; a probe that took the locks made lock files in a folder the command then refused to touch, so "Nothing was changed." was false. (3) A menu-bar app starting, or re-taking its lock at a refresh, in the probe's instant would otherwise quit as "already running" while nothing runs or is removed.

**Rejected alternatives.** Judging the engine's lock by the unit file (an installed but stopped service hid a terminal run; a loaded job without its file was read as one). A non-holding probe with fcntl `F_GETLK` (does not see flock holders). Retrying at the next poll instead of after a moment (the app would run unlocked beside a real second instance meanwhile). Renaming the folder away before taking it apart, so that nobody finds it by name meanwhile (files the person kept in it, which the removal must leave, would travel into a renamed folder; the folder is where they look for them).

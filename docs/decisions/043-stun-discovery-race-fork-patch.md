# 043 — The STUN and NAT-PMP cancel races get fork patches; no Syncthing upgrade removes them

**Context.** `go test -race` failed the bridge suite on a data race in the pinned Syncthing (#152). The QUIC listener runs a STUN service whose `runStunForServer` wraps the blocking NAT discovery in `svcutil.CallWithContext`, which returns as soon as the context is canceled while the discovery finishes on its own goroutine — and the discovery closure assigned the caller's `err`, which the returning call assigns, reads and returns. The path is live on iOS: the default listen addresses include QUIC, the bridge forces `natEnabled`, and a discovery runs for several seconds after every engine start (go-stun retransmits for up to ~9.5 s per unanswered test), so a stop in the middle of one is routine. No crash or sync fault has been traced to it; the read side can see a torn two-word interface value, which Syncthing's logging adapter formats on every call, whatever the log level. The same capture sits in `lib/pmp` (#195): the NAT-PMP device's `AddPortMapping` and `GetExternalIPv4Address` run their request through `CallWithContext` and read the request's `result` after the call whatever its error, while the request may still assign it. The NAT service passes its own context, so an engine stop during a request to a gateway that speaks NAT-PMP is the trigger; both callers discard the value when the call reports an error, which a stop always does, so nothing a user sees can change.

**Decision.** Fork patch `005-stun-discovery-cancel-race`: the closure gets its own error variable. `natType` and `extAddr` stay shared, because the caller reads them only after the call has completed. `TestIssue152_StopDuringStunDiscoveryIsRaceFree` holds a real `stun.Service`'s discovery in flight, stops the service, and lets the discovery finish only after `Serve` has returned; it waits by polling the goroutine dump, because waiting on a channel would create exactly the happens-before edge that hides the race. The race detector is its oracle, so CI runs it with `-race`. A Syncthing bump carries 005 forward and drops it only once upstream changes the closure and the test stays green under `-race`. Fork patch `010-natpmp-result-after-cancel` (#195) reads `result` only when `CallWithContext` returned nil, which it does only from its completed branch, after the closure's write; go-nat-pmp never returns a result together with an error, so every value the methods return is unchanged. `TestIssue195_StopDuringNATPMPRequestIsRaceFree` holds a real request at a NAT-PMP gateway on loopback (127.0.0.1:5351, the protocol's fixed port) and lets it be answered only after the call has returned, with the same goroutine-dump wait; `TestIssue195_AnsweredNATPMPRequestReturnsTheAnswer` keeps the answered path. lib/pmp's device type is unexported and `pmp.Discover` builds it only for the machine's real default gateway, so the test copies its fields and calls its methods by their linker names; before the first call it parses `lib/pmp`'s source and fails unless the type and both signatures match the copy. CI runs both tests with `-race` beside #152's, and a bump carries 010 like 005.

**Why.** Upstream `main`, v2.1.5 and v2.1.6-rc.4 carry a byte-identical `lib/stun/stun.go`, and no upstream issue or PR about the race was found, so no available version removes it; the patch touches one closure and is small enough to upstream. The same holds for 010: upstream `main` and v2.1.7 carry the same reads in `lib/pmp/pmp.go`, and no upstream issue or PR about them was found.

**Rejected alternatives.** Upgrading Syncthing to resolve #152: it does not remove the race, and v2.1.5 is 167 commits ahead and changes the upstream files under patches 001 (`dynamic.go`), 002 (`noassets.go`), and 003 and 004 (`service.go`) — the upgrade stays a separate change. Changing `svcutil.CallWithContext` to hand results through its channel: its own synchronization is correct, the defect is the caller's capture, and a new signature would ripple into `lib/pmp`. Calling `Discover` without the goroutine, or waiting for it: `Serve` would stop returning promptly on cancel and sit out go-stun's retransmit schedule whenever the connection does not close first — the regression test's non-race assertion guards exactly that. For #195, a closure-local result as in 005: the caller needs the value, and a local reaches it only through the shared write that races. Waiting for the request after a cancel: the NAT service's stop would sit out the client's timeout (`NATTimeoutS`, 10 s by default) — the test's non-race assertion that the call returns while the gateway still holds its answer guards that. A test seam added by the patch, or a test inside the fork: the test could then not fail without the patch, so it would not catch a bump that drops it.

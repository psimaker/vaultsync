# 043 — The STUN discovery race gets a fork patch; no Syncthing upgrade removes it

**Context.** `go test -race` failed the bridge suite on a data race in the pinned Syncthing (#152). The QUIC listener runs a STUN service whose `runStunForServer` wraps the blocking NAT discovery in `svcutil.CallWithContext`, which returns as soon as the context is canceled while the discovery finishes on its own goroutine — and the discovery closure assigned the caller's `err`, which the returning call assigns, reads and returns. The path is live on iOS: the default listen addresses include QUIC, the bridge forces `natEnabled`, and a discovery runs for several seconds after every engine start (go-stun retransmits for up to ~9.5 s per unanswered test), so a stop in the middle of one is routine. No crash or sync fault has been traced to it; the read side can see a torn two-word interface value, which Syncthing's logging adapter formats on every call, whatever the log level.

**Decision.** Fork patch `005-stun-discovery-cancel-race`: the closure gets its own error variable. `natType` and `extAddr` stay shared, because the caller reads them only after the call has completed. `TestIssue152_StopDuringStunDiscoveryIsRaceFree` holds a real `stun.Service`'s discovery in flight, stops the service, and lets the discovery finish only after `Serve` has returned; it waits by polling the goroutine dump, because waiting on a channel would create exactly the happens-before edge that hides the race. The race detector is its oracle, so CI runs it with `-race`. A Syncthing bump carries 005 forward and drops it only once upstream changes the closure and the test stays green under `-race`. 005 covers STUN only: the full race suite also caught `lib/pmp` reading a call's result after a canceled `CallWithContext` — the same capture pattern, tracked as #195.

**Why.** Upstream `main`, v2.1.5 and v2.1.6-rc.4 carry a byte-identical `lib/stun/stun.go`, and no upstream issue or PR about the race was found, so no available version removes it; the patch touches one closure and is small enough to upstream.

**Rejected alternatives.** Upgrading Syncthing to resolve #152: it does not remove the race, and v2.1.5 is 167 commits ahead and changes the upstream files under patches 001 (`dynamic.go`), 002 (`noassets.go`), and 003 and 004 (`service.go`) — the upgrade stays a separate change. Changing `svcutil.CallWithContext` to hand results through its channel: its own synchronization is correct, the defect is the caller's capture, and a new signature would ripple into `lib/pmp`. Calling `Discover` without the goroutine, or waiting for it: `Serve` would stop returning promptly on cancel and sit out go-stun's retransmit schedule whenever the connection does not close first — the regression test's non-race assertion guards exactly that.

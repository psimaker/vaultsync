# 082 — The path repair never makes two folders overlap

**Context.** Two folders never overlap on disk — not one directory, not one inside the other (001). The bridge held that when a folder is added or accepted (`AddFolder`, `AcceptPendingFolder`, `folderPathOverlapError`). `SetFolderPath`, the repair that re-points a folder whose directory is gone (003, 063), compared the new path with no other folder: the folder's own directory under a new path was taken also where it is another folder's directory, lies inside one or holds one (`TestIssue330_…`, red before this change). Two ways lead there. An install from before 1.7.2 can hold a pair that already overlaps — paused once by the launch shield, perhaps resumed on purpose since — and when the container's path changes, the repair re-points both, back into their overlap. And the folder's own directory can come to be, hold or lie in another folder's directory while the folder cannot reach it — for one, a share accepted there with the confirmation that it may be combined with what the directory holds (007). The shield did not stop either: it runs after the repair, when the folder has already restarted at its new path; it never pauses again a folder it paused once; and a background run repairs paths without it.

**Decision.** (1) `SetFolderPath` holds the floor of `AddFolder`: it refuses a path that is another configured folder's path, lies inside one or holds one — whichever folder, paused or not, its directory there or not. Every such overlap is refused, also one that was there before the move. The check comes after the marker, the folder's own directory and the record of its directory (063), and before anything is written. A refusal leaves the folder where it is; a path that is already the configured one is no write and stays a no-op. The refusal has one text, which the bridge hands out (`FolderPathOverlapError`). (2) Of a pair that overlapped before, the folder the repair reaches first goes on in its directory; the other stays at its old path, a folder whose directory is gone. Nothing is paused, moved or deleted for it, and the shield's record is left as it is (002). (3) The reconcile reports the refusal (`SetPathResult.overlapsAnotherFolder`, `Outcome.overlapsAnotherFolder`), as it reports a copy (063). The vault's card under Sync Issues and its own page say that the vault's folder was found, but that another vault already syncs it, a folder inside it or a folder around it; that two vaults never sync in one place; and the way on: remove this vault, wait ten seconds, close VaultSync and open it again, accept the vault again — it gets a folder of its own — and never combine it with what a folder already holds. The card links to a section of its own in the troubleshooting guide.

**Why.** The repair writes a folder's path as an add and an accept do, and 001's floor is there to hold whatever the layers above it compute: the repair was the one write without it. Refusing only "an overlap that did not exist before" needs to know what was before, and the bridge does not. The other folder of a pair may have been re-pointed earlier in the same pass, so the configured paths no longer show how the two lay; the reconciler's mapping is the derived state 003 does not trust; and the shield's record says that a pause happened, not that the user agreed to an overlap. An overlap is damage (001, 002): the outer vault syncs the inner vault's notes as its own, and a deletion of that stray copy on any device reaches the inner vault everywhere. A resume was a step of its recovery, which the shield respects by never pausing again; it was no consent to set the overlap up anew in another place, where the shield would find a folder it has handled and do nothing. The refusal costs one vault that stops syncing on this iPhone, with a card and the manual way out, and deletes nothing on any device. And only the floor holds where the shield does not run: in a background run, and in the moment between the repair and the pause.

**Rejected alternative.** *Refusing only an overlap that did not exist before the move* — the issue's other option: known only through derived state (above), and with it the bridge itself would set up again, unpaused, an overlap the user had resumed. *Leaving the refusal to the reconcile's existing failure path:* the vault's card would say that its storage no longer exists and offer to reconnect, and a reconnect repeats the refusal. *Re-pointing and pausing the second folder:* the folder would be re-pointed into the overlap first (003), and a pause the user lifts leaves the overlap in place.

**Not covered.** Which folder of a pair goes on depends on the order in which the reconcile meets them, the order of the bridge's folder list (#345 makes it stable). A pair that overlaps and does not move stays as it is, in the shield's care. A pair the shield paused: the folder that goes on stays paused, and the card under Sync Issues is the other one's. The floor compares the configured paths cleaned and without regard to case, and does not resolve symbolic links (`/var` and `/private/var`), like the floor in `AddFolder` and `AcceptPendingFolder`.

# 082 — The path repair never makes two folders overlap

**Context.** Two folders never overlap on disk — not one directory, not one inside the other (001). The bridge held that when a folder is added or accepted (`AddFolder`, `AcceptPendingFolder`, `folderPathOverlapError`). `SetFolderPath`, the repair that re-points a folder whose directory is gone (003, 063), compared the new path with no other folder: the folder's own directory under a new path was taken also where it is another folder's directory, lies inside one or holds one (`TestIssue330_…`, red before this change). Two ways lead there. An install from before 1.7.2 can hold a pair that already overlaps — paused once by the launch shield, perhaps resumed on purpose since — and when the container's path changes, the repair re-points both, back into their overlap. And the folder's own directory can come to be, hold or lie in another folder's directory while the folder cannot reach it — for one, a share accepted there with the confirmation that it may be combined with what the directory holds (007). The shield did not stop either: it runs after the repair, when the folder has already restarted at its new path; it never pauses again a folder it paused once; and a background run repairs paths without it.

**Decision.** (1) `SetFolderPath` holds the floor of `AddFolder`: it refuses a path that is another configured folder's path, lies inside one or holds one — whichever folder, paused or not, its directory there or not. Every such overlap is refused, also one that was there before the move. The check comes after the marker, the folder's own directory and the record of its directory (063), and before anything is written. A refusal leaves the folder where it is; a path that is already the configured one is no write and stays a no-op. The refusal has one text, which the bridge hands out (`FolderPathOverlapError`). (2) The reconcile does not leave it to the order of the folder list. Before it asks the bridge for any repair in a pass, it holds every repair it is about to ask for against the other folders. Where the new paths of two repairs overlap, both are held. A repair whose new path is, holds or lies in the configured path of a folder that is not being repaired is held too: that folder stays there. Every repair whose new path exists counts, whether or not the folder's marker is there: a version that put two folders into one directory left a marker file for the first only, because the engine writes one only where `.stfolder` is missing (`TestIssue330_TheEngineMarksOnlyTheFirstFolderOfADirectory`), and a pair must not come apart over that. So neither folder of a pair that overlapped before is re-pointed. Each stays at its old path, a folder whose directory is gone, and gets the card until one of the two is removed; the next reconcile then repairs the other. A repair whose new path overlaps only the old path of a folder that is itself being repaired in the same pass is not asked for and gets no card: the vault looks as it did, and the next pass repairs it once that folder has moved away. Holding the other folder as well would keep both where they are for good, and the card would tell the person to remove a vault that comes back by itself. This lives in the reconcile's pure core, so the foreground pass and the background runs hold alike; the bridge's floor stays under it. Nothing is paused, moved or deleted for a held or refused folder, and the shield's record is left as it is (002). (3) The reconcile reports both its own hold and the bridge's refusal (`Outcome.overlapsAnotherFolder`, `SetPathResult.overlapsAnotherFolder`), as it reports a copy (063). The vault's card under Sync Issues and its own page say that the vault's folder was found, but that it is another vault's folder too, or lies inside or around one; that two vaults never sync in one place, and that when one of the two is removed the other goes on there; and the way on: remove this vault, wait ten seconds, close VaultSync and open it again, accept the vault again — it gets a folder of its own — and never combine it with what a folder already holds. The card offers no reconnect: the vault's own folder was found, so no other selection holds it. It links to a section of its own in the troubleshooting guide. A return to the app reconciles again while the card shows, which is what repairs the vault once the other one is removed; share accepts wait for that pass (008).

**Why.** The repair writes a folder's path as an add and an accept do, and 001's floor is there to hold whatever the layers above it compute: the repair was the one write without it. Refusing only "an overlap that did not exist before" needs to know what was before, and the bridge does not. The other folder of a pair may have been re-pointed earlier in the same pass, so the configured paths no longer show how the two lay; the reconciler's mapping is the derived state 003 does not trust; and the shield's record says that a pause happened, not that the user agreed to an overlap. An overlap is damage (001, 002): the outer vault syncs the inner vault's notes as its own, and a deletion of that stray copy on any device reaches the inner vault everywhere. A resume was a step of its recovery, which the shield respects by never pausing again; it was no consent to set the overlap up anew in another place, where the shield would find a folder it has handled and do nothing. The refusal costs one vault — or both of a pair — that stops syncing on this iPhone, with a card and the manual way out, and deletes nothing on any device. And only the floor and the reconcile hold where the shield does not run: in a background run, and in the moment between the repair and the pause. The floor alone cannot know where another folder is about to go: in a container move each folder of a pair still has its old path until its own repair, so the floor takes whichever folder comes first. The reconcile knows every new path before it asks for any, so it can hold both. A nested pair held that way also keeps its configured paths nested, and with them the shield's banner and its recovery steps.

**Rejected alternative.** *Refusing only an overlap that did not exist before the move* — the issue's other option: known only through derived state (above), and with it the bridge itself would set up again, unpaused, an overlap the user had resumed. *The floor alone, the folder it meets first going on* — the first form of this record, which fell in review. Which folder comes first followed the order of the bridge's folder list, which has none. With the outer folder first, that folder was re-pointed onto a directory that holds the inner vault's folder, notes and marker, and synced them as its own; the nested banner with its recovery steps was gone, since the configured paths no longer nested. *Leaving the refusal to the reconcile's existing failure path:* the vault's card would say that its storage no longer exists and offer to reconnect, and a reconnect repeats the refusal. *Re-pointing and pausing the second folder:* the folder would be re-pointed into the overlap first (003), and a pause the user lifts leaves the overlap in place.

**Not covered.** A pair that overlaps and does not move stays as it is, in the shield's care. A pair the shield paused stays paused; when one of the two is removed, the other goes on paused. A repair counts even where the bridge would refuse it for another reason — a copy (063) — and can hold the other folder of a pair back with it: that vault shows the overlap card instead of the copy card, which errs on the careful side. A repair that waits on a folder which is itself held waits, without a card, for as long as that folder is held. The floor compares the configured paths cleaned and without regard to case, and does not resolve symbolic links (`/var` and `/private/var`), like the floor in `AddFolder` and `AcceptPendingFolder`. The reconcile compares paths with links resolved where the path exists, and with a leading `/private` dropped in every case, so a folder's old path that is gone compares in the same form as a new path that exists; the floor stays under it.

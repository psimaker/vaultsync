# 046 — The desktop agent runs its own pinned Syncthing; cloud folders are a hard block

**Context.** M3 (#175): "1) Obsidian device" must work on a computer without Syncthing. The agent `vaultsync` (module `desktop/`) pairs with a Hub through `hub/pairing` (decision 045) and accepts shares through the device-side guard lifted from the Hub CLI into `hub/join` (`acceptShareLocally`, unchanged, now shared by both commands).

**Decision.** (1) One stock Syncthing release is pinned in the binary (`desktop/pins.go`, v2.1.6 at first) with the SHA-256 of each platform's archive; the download is compared with that pin before anything is unpacked, and a mismatch installs nothing. The installed binary's own hash is recorded and re-checked before every start. A pin bump is a reviewed change: version, the four checksums from the release's signed `sha256sum.txt.asc` cross-checked against GitHub's asset digests, a green Desktop Syncthing E2E. (2) The engine is a child process of `vaultsync run` with a private home, `--no-restart`/`--no-upgrade`, no default folder, its REST API on 127.0.0.1 with the key from its own `config.xml` (never on a command line) and a web UI password nobody knows; the agent owns restarts, the service manager (launchd LaunchAgent / systemd `--user`) owns the agent. (3) A Syncthing the user already runs is never adopted, started, stopped or written to; the agent only reads its `config.xml` to stay off port 22000 and to refuse a folder it already syncs — an unreadable one fails closed. (4) Vaults inside iCloud Drive, OneDrive, Dropbox, Google Drive, Nextcloud (their default places, every `~/Library/CloudStorage` domain, and the folders the clients' own settings name) — or containing one — are refused, not warned about. (5) A folder that holds files syncs only after consent and only with a vault this pairing started: absent from a catalogue fetched right before, created by `create`, shared with this computer alone, reporting no files; every check runs again after the last wait, right before the folder is added.

**Why.** A user's Syncthing has its own folders, devices and upgrade cadence; driving it means the agent's mistakes land in a configuration it does not own, and its auto-upgrades would change the engine under the doctrine's tests. A pin makes the engine a reviewed input, like the iOS fork. Cloud clients turn not-yet-downloaded files into placeholders, and a placeholder that disappears reads as a deletion that Syncthing sends to every device — no warning undoes that.

**Rejected alternatives.** Reusing an installed Syncthing (the setup.sh path before #175; stays available as `vaultsync-hub pair`). Fetching checksums next to the download (a compromised host serves both). A warning for cloud folders (iOS warns, #95; on a desktop the placeholder risk is the default for iCloud and OneDrive). Refusing every folder with files until the Hub has an atomic create-only step (#206): the first computer could not bring its vault at all; the residual race (an operator `vault adopt` of the same name, or a `vaultsync-hub pair --path` device, within the seconds between the checks) is recorded here and closes with #206.

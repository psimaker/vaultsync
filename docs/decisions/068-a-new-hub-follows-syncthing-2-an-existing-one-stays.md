# 068 — A new Hub follows Syncthing 2.x; an existing Hub stays on the line its `.env` names

**Context.** The Hub's stack named `syncthing/syncthing:1` (#301). That tag has stood at 1.30.0 since 2025-07-01, the last release of the 1.x line, while the app's engine and the desktop agent run 2.x. Syncthing 2.x converts a 1.x database on its first start (`index-v0.14.0.db` becomes `index-v0.14.0.db-migrated` plus `index-v2`), and 1.30.0 then refuses to start on that home ("config file version (52) is newer than supported version (37)"), observed with both images on one directory on 2026-11-15. `setup.sh` writes `docker-compose.yml` anew on every run, so a changed image line reaches every existing Hub at its next setup run.

**Decision.** The compose file takes Syncthing's image from `.env` — `image: ${VAULTSYNC_HUB_SYNCTHING_IMAGE:-syncthing/syncthing:1}` — and falls back to 1.x without that line. A new `.env` names `syncthing/syncthing:2`. Setup writes `.env` only when there is none and never edits that line, so every Hub set up before keeps 1.x until its owner moves it. When setup writes a new `.env` into a Hub directory where a Syncthing already ran (its `.env` lost), it names 2.x only if it sees 2.x's own database there (`syncthing/config/index-v2`). Anything else, including a folder it cannot look into (Syncthing keeps its folder 0700), keeps 1.x. Setup unsets an exported `VAULTSYNC_HUB_SYNCTHING_IMAGE`, as it does `VAULTSYNC_HUB_IMAGE` (#216), because Compose ranks the shell above `.env`. The tag is the major line, `:2`, not a pinned release. The Hub and helper images are pinned because each of their releases is ours, while Syncthing's fixes within a major line should reach a Hub with `docker compose pull`. The `.env` line is also what holds a Hub back from a later `:3`.

**Why.** A move from 1.x to 2.x cannot be undone without the data of the 1.x database. Each guess therefore fails toward 1.x. A wrong 1.x on a 2.x home stops the Hub with a clear log line and loses nothing. A wrong 2.x on a 1.x home converts its database for good. Before the change, the Hub's end-to-end test passed with a stock 2.1.7 binary, at `main` and at `hub-v0.3.0`. A Hub set up with the setup link on `:2` paired a vault, and the helper read its configuration and noticed a change to a note.

**Rejected alternatives.** Changing the image line to `:2` outright would have moved every existing Hub at its next setup run without asking. A `:2` default in the compose file, with setup appending `:1` to each existing `.env`, fails open. An `.env` that setup refuses to edit (quoted values, a link, a hand-made shape — #216's rules) would move, and so would a stack started from the compose file without setup. Detecting a 1.x database by its file alone fails open too, since the folder is 0700. Pinning `syncthing/syncthing:2.1.7` would mean a Hub release for every Syncthing fix.

**Links.** #301, #297; decision 003 (never re-point a live folder) for the same one-way-door reasoning; `hub/docker-compose.yml`, `hub/scripts/setup.sh` (`syncthing_image_for_new_env`), `hub/scripts/tests/setup-dry-run-test.sh`; `docs/hub.md` → Update the Hub. Moving an existing Hub to 2.x, with its owner's consent and a documented step, is a separate item.

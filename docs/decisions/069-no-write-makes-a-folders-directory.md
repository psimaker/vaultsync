# 069 — No write of a folder's filters makes its directory

**Context.** Once per launch the app writes its default ignore patterns into every vault (`applyDefaultIgnoresIfNeeded` → the bridge's `EnsureDefaultIgnores`), and two seconds after an add or an accept as well; the Sync Filters screen writes `.stignore` through `SetFolderIgnores`. Both end in the engine's `setIgnores`, which upstream makes the folder's directory when it is missing (`CreateRoot`, a `MkdirAll`) and writes into a directory without the marker. A vault whose folder was moved or deleted while VaultSync was closed got an empty folder of its name back at its old place on the next launch (#371, seen on a device). The engine then reported the marker missing instead of the path missing, so the vault lost "Reconnect to Obsidian", and the path reconcile took the new directory for the vault's own, so selecting the folder the vault had been moved into did not move it there.

**Decision.** (1) A folder's `.stignore` is written only while the engine's own `CheckPath` passes for the path the folder has at that moment: the directory exists, is a directory and holds the marker entry. (2) The bridge asks it before `EnsureDefaultIgnores` or `SetFolderIgnores` reads or writes anything (`folderDirectoryRefusal`) and refuses with a text that contains "marker missing" and no path, which the app shows as a vault whose folder was moved or deleted. (3) The engine's `setIgnores` asks it again and returns its error instead of making the root (fork patch 006), which the bridge words the same way (`ignoresWriteError`), so a folder taken away between the two, or a writer that reaches the engine without the bridge, makes nothing either. (4) Nothing makes the directory or the marker of a folder that exists; a directory an earlier version made this way stays until its owner deletes it (002).

**Why.** That a folder's directory exists is evidence: the engine's error, the path reconcile and the record of #315 all read it, and a write that makes the directory forges it. `CheckPath` is the engine's own rule for a folder it syncs, so no folder the engine syncs is refused. A new vault holds its marker before its add or accept returns — the engine makes it inside the configuration commit the bridge waits for — so its defaults still land two seconds later (`TestEnsureDefaultIgnores`, `TestIssue371_ANewVaultGetsItsDefaultsRightAfterTheAccept`).

**Rejected alternatives.** *A check in the app before it asks the bridge:* it reads the path the app captured, which is the old one for a vault the reconcile re-points a moment later, so that vault went without its defaults for the rest of the process; and it repeats a rule the bridge and the engine already hold at the moment of the write. *Checking only that the directory exists:* a directory without the marker — one made by hand in the vault's place, or the one #371 left behind on an install that ran an earlier version — would still be written into. *The marker's fingerprint file, as `SetFolderPath` checks it:* a folder accepted into a directory that already held a `.stfolder` never gets one, and the engine syncs it; its filters would be refused for no gain, since no write here re-points anything. *The bridge's check alone, without the patch:* the engine looks again inside its own write, and a folder taken away in between was still made.

**Not covered.** A folder with nothing in its index is new to the engine, which makes its directory and marker again at its next start (#338); that path is the engine's and is not changed here. The engine's own auto-accept makes a folder's directory but not its marker before it writes its default patterns, so it never gets them; VaultSync never turns auto-accept on. A vault refused at launch because its folder was gone, and re-pointed later in the same process with "Reconnect to Obsidian", is not asked again until the next launch; the folder it was moved with carries the `.stignore` it had.

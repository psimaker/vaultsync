# Changelog — VaultSync for Mac and Linux

The desktop agent `vaultsync`, VaultSync for Mac and the menu-bar app, released as `desktop-vX.Y.Z` tags. The iOS app, the Hub and the wake-up helper are in the [root changelog](../CHANGELOG.md).

---

## [0.2.0] — 2026-11-05

### Added

- **On a Mac the setup link installs VaultSync for Mac, which runs the background service and opens the menu-bar icon at every login** ([#254](https://github.com/psimaker/vaultsync/issues/254)) — **1) Obsidian device** puts VaultSync for Mac into Applications (into `~/Applications` when your account cannot write there) and runs the setup from the app: the background service then runs from VaultSync for Mac, which macOS lists under Login Items, and the menu-bar icon opens when you log in — again by itself after a crash, not after you quit it. An existing service moves into the app once, which may make macOS ask once more for its permissions; the `vaultsync` command follows. An app of that name that is not VaultSync for Mac is never replaced, and with the app installed a `vaultsync` of another build (from this release on) stops and says to update the app instead of moving the service; and VaultSync's own copy does not sync beside an installed VaultSync for Mac at all — it stops within seconds of the app's arrival and stays so until the setup link (or the copy's own setup, without the app) sets it up anew; `vaultsync status` says so, and says it too when an older VaultSync left the service on its copy beside the app. Keep the app in Applications while VaultSync is set up — moved or put in the Trash, VaultSync stops syncing within seconds until the app is back where it was, and VaultSync's own copy (`~/Library/Application\ Support/VaultSync/bin/vaultsync status`) says so with the way back; `vaultsync uninstall` also quits the icon and removes its start at login (`--remove-data` no longer asks you to quit an icon VaultSync started), and points the `vaultsync` command back at that copy before the app goes to the Trash. `launchctl disable gui/$(id -u)/eu.vaultsync.tray` keeps only the icon from opening at login, and the setup leaves that so. An update never leaves you without a working app: the new one must run on your Mac before it takes the old one's place, and an update that stops halfway puts the old one back. A release without the app is set up with the bare agent, as before. Recorded in decision 053.
- **A menu-bar icon for VaultSync on a Mac or Linux computer** ([#176](https://github.com/psimaker/vaultsync/issues/176)) — `vaultsync-tray`, from the same release as the desktop agent, shows at a glance what `vaultsync status` says: a check mark when every vault is up to date, a ring while syncing, two bars while paused, an exclamation mark when a vault needs attention, a crossed ring when nothing syncs. The menu lists your Hub and each vault with the very words `status` prints (click a vault to open its folder), pauses and resumes syncing like `vaultsync pause` and `resume`, opens the service's log on a Mac, and pairs a vault through the desktop's own dialogs — the code, the choice of vault, and for a folder that already holds files the same consent the terminal asks for. It asks the running agent for everything over the socket the terminal uses and decides nothing itself; Quit closes the icon only, syncing goes on. On a Mac it comes as VaultSync for Mac (`VaultSync_darwin_<arch>.zip`, no Dock icon), which the setup link installs and opens at every login ([#254](https://github.com/psimaker/vaultsync/issues/254)); on Linux as `vaultsync-tray_linux_<arch>`, which you start yourself; on GNOME it names the extension that tray icons need, on Linux its dialogs need `zenity`; `vaultsync uninstall --remove-data` asks you to quit one you opened yourself first, before it removes the background service. Recorded in decisions 048 and 050.
- **Pause and resume syncing on a Mac or Linux computer without stopping the service** ([#176](https://github.com/psimaker/vaultsync/issues/176)) — `vaultsync pause` pauses every connection of the desktop agent to your Hub (nothing new arrives or leaves; the engine keeps running, your vaults and their settings stay as they are, and changes already received may still be applied for a moment) and `vaultsync resume` takes it back; `vaultsync status` says `paused on this computer` meanwhile and keeps showing what is still in progress. The running agent now answers status, pause, resume and pairing over a socket in VaultSync's folder, readable by your account alone — the one truth the menu-bar app shows.

### Changed

- **`vaultsync uninstall --remove-data` refuses before it removes the background service while VaultSync is in use, and says what stays** ([#176](https://github.com/psimaker/vaultsync/issues/176)) — with a menu-bar app you opened yourself running, or a `vaultsync run`, `pair` or `setup` in progress, it refuses before the service goes instead of removing it first and refusing after (on a Mac it may have removed the menu-bar icon's start at login by then, and says so); on a Mac it must be run from your own session, since it asks the service manager; it lists what it removed, names a folder it could not remove as an error (exit status 1), a folder that holds files VaultSync did not make as kept, and a folder that went meanwhile as gone. A `vaultsync run` that waited for VaultSync's folder while it was removed no longer sets VaultSync up afresh.
- **`vaultsync setup` and `pair` with `--create` no longer download a Hub vault of the same name** ([#176](https://github.com/psimaker/vaultsync/issues/176)) — `--create` asks for a new vault on your Hub; when your Hub already has one of that name, the agent now refuses and says to download that vault as the Hub's or to choose another name, instead of quietly downloading it into the folder (an empty folder would have received a vault you did not choose). A setup run again with the same flags still finds the vault it set up before and succeeds ([#228](https://github.com/psimaker/vaultsync/issues/228)).
- **VaultSync for Mac is signed with a Developer ID and notarized by Apple — a permission you give it stays given after an update** ([#222](https://github.com/psimaker/vaultsync/issues/222)) — the desktop agent `vaultsync` and VaultSync for Mac are signed with a Developer ID, run with the hardened runtime and are notarized by Apple (the app with its ticket stapled). macOS ties a permission such as access to Documents or the local network to that signature, so it now carries over to later releases instead of being asked for again after each update — once more when you move from an older, unsigned release, and possibly once when the background service moves into VaultSync for Mac ([#254](https://github.com/psimaker/vaultsync/issues/254)). A copy a web browser downloaded runs too; before, macOS blocked it. Recorded in decision 052.
- **The setup link sets up a Mac or Linux computer with VaultSync for Mac and Linux — no Syncthing to install first** ([#213](https://github.com/psimaker/vaultsync/issues/213)) — `curl -fsSL https://vaultsync.eu/setup.sh | sh` → **1) Obsidian device** downloads the desktop agent from its newest release (never a pre-release), checks it against that release's `SHA256SUMS` and runs its setup, which asks for the code and the vault; arguments after `--` go to the agent for scripts, and a dry run never prints the code, in whichever spelling it was passed. A Syncthing you already run is never touched; to pair that Syncthing itself with your Hub, use `vaultsync-hub pair` (see docs/hub.md). The link itself works again: it answered 404 until the landing page got its redirect ([#219](https://github.com/psimaker/vaultsync/issues/219)).
- **Updated the Go runtime the desktop agent is built with** — Go 1.26.6 → 1.26.10 with the latest standard-library security fixes; the [root changelog](../CHANGELOG.md) lists them.

### Fixed

- **An older VaultSync never puts an older sync engine back** ([#264](https://github.com/psimaker/vaultsync/issues/264)) — the desktop agent installs the Syncthing it was built with; a `vaultsync` older than the one set up on the computer (an old download, an older VaultSync for Mac dragged into Applications, a copy left behind) now stops and says to run the setup link, instead of installing its older Syncthing over the state the newer one wrote. Nothing is changed; the background service of such a build does not sync until the current VaultSync is back, and its `vaultsync status` says it is older; `vaultsync start` no longer judges a service that runs another build by its own version: it says so, and `vaultsync status` tells whether it syncs. desktop-v0.1.0, which knows nothing of this, no longer sets up or runs once this release's setup has taken over — use the setup link; until then a desktop-v0.1.0 that is still installed keeps running beside this release's `pair`, and a `run` it refuses changes nothing. Recorded in decision 054.
- **The menu-bar app says when macOS holds up opening a vault** ([#255](https://github.com/psimaker/vaultsync/issues/255)) — opening a vault in Documents, Desktop or Downloads from the menu makes macOS ask once whether VaultSync for Mac may open folders there; the menu waited half a minute for that answer, then showed nothing, and the folder did not open when you answered. It now says that macOS may be asking and to click the vault again once you have answered, and the note goes once the vault has opened. A vault folder whose name ends like an app (`Journal.app`) is shown in the Finder, never opened as an app — also when macOS does not let the menu look at it.
- **`vaultsync status` no longer calls the background service stopped when you are simply not logged in yet** ([#232](https://github.com/psimaker/vaultsync/issues/232)) — on a Mac reached over SSH before anyone logged in at the screen (and on Linux when your systemd user manager is not running — your last session ended without `loginctl enable-linger`), the service has no session to run in: `status` and `start` now say that it waits for your login, instead of sending you to `vaultsync start` or printing the service manager's error.
- **Running the desktop agent's setup again with the same flags no longer refuses with a folder that “overlaps itself”** ([#228](https://github.com/psimaker/vaultsync/issues/228)) — a script that runs `vaultsync setup --vault X --path P` a second time now hears that X is already set up to sync at P and succeeds, with no second share request to the Hub and no change on this computer; naming another folder for a vault that is already set up here says where it is instead. Every other overlap is refused as before.

## [0.1.0] — 2026-10-06

### Added

- **VaultSync for Mac and Linux: a desktop agent that brings its own Syncthing** ([#175](https://github.com/psimaker/vaultsync/issues/175)) — one program, `vaultsync`, turns a computer without Syncthing into a VaultSync device: `vaultsync setup` downloads Syncthing 2.1.6 and installs it only when it matches the checksum built into VaultSync, runs it in the background with its own settings (a LaunchAgent on macOS, a systemd user service on Linux; no administrator rights), pairs with your Hub by code — asking which Hub printed it when several answer, and sending the code only there — and offers your Obsidian vaults (newest first, from Obsidian's own list) next to the vaults on your Hub. A Hub vault arrives in a new, empty folder; a vault from this computer becomes a new vault on your Hub, and a folder that already holds files syncs only after you agree to sync that very folder, and only with a vault your Hub reports as new, empty and shared with this computer alone — the agent checks everything again, here and on the Hub, right before it connects the folder. Vaults inside iCloud Drive, OneDrive, Dropbox, Google Drive or Nextcloud are refused, because their placeholder files would sync as deletions. A Syncthing you already run is never touched; folders it syncs are never synced twice. `vaultsync status`, `pair`, `stop`/`start` and `uninstall` (your vaults always stay) complete it; Windows follows. Documented in `docs/hub.md`; recorded in decision 046. Shipped as `desktop-v*` releases.

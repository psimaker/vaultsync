# Changelog — VaultSync for Mac and Linux

The desktop agent `vaultsync`, VaultSync for Mac and the menu-bar app, released as `desktop-vX.Y.Z` tags, and what the setup link's **1) Obsidian device** changes, which is live once merged. The iOS app, the setup link's **2) Hub**, the wake-up helper and what spans all of them are in the [root changelog](../CHANGELOG.md); the Hub's image and `vaultsync-hub` in the [Hub's changelog](../hub/CHANGELOG.md).

---

## [Unreleased]

### Fixed

- **An interrupted update through the setup link removes only its own VaultSync for Mac** ([#268](https://github.com/psimaker/vaultsync/issues/268)) — the setup link sets the installed VaultSync for Mac aside, moves the new one into its place and puts the old one back if the update stops on the way: Ctrl-C, a closed Terminal, a move that fails. It then removed whatever stood at the app's place, also what another setup running at the same time, or you, had put there meanwhile, such as that setup's app or a file. Now it removes only the app it moved there itself. Anything else stays as it is, and the setup says so and where the app it set aside is kept. It also looks at the place again right before the set-aside, and checks what it set aside, so it never sets aside, and later removes, something that is not VaultSync for Mac. The change is live once merged, because the setup link serves the main branch.
- **From this release on, an older VaultSync no longer pairs or removes anything beside a newer one** ([#281](https://github.com/psimaker/vaultsync/issues/281)) — where a newer VaultSync is set up on this computer, an older one, such as an old download or an older VaultSync for Mac put back in Applications, already refused to set up or run its older sync engine. `vaultsync pair` and `uninstall` did not check. An older `pair` paired through the newer engine with its own older checks and rewrote VaultSync's record in its own shape. An older `uninstall` run from the app put its own program over VaultSync's copy. Beside a newer record, `pair`, `pause` and `resume` ended on a bare format error. `pair` and `uninstall` now change nothing and say so. `pause` and `resume` still work where the running VaultSync answers, which does the pausing, and otherwise say the same. The message names the program that holds the VaultSync set up here, such as VaultSync's own copy or VaultSync for Mac's, with the command and the options you gave, or the setup link where none is found. `uninstall` and `pause` also say how syncing stops now: `stop`, where a background service is installed. The menu-bar app of an older VaultSync now says that it is older and to run the setup link, where it said that VaultSync's settings were damaged. `vaultsync status` of such a build no longer says that moving the app to the Trash will not stop a service that does not sync. Releases before this one keep their behaviour. Recorded in decision 091.
- **The setup link no longer replaces a newer VaultSync for Mac with an older release** ([#277](https://github.com/psimaker/vaultsync/issues/277)) — the setup link installs the newest release of VaultSync for Mac and replaced any other build in Applications with it, a newer one too. Had a release been withdrawn after it reached your Mac, the link would have put the release before it in its place, removed the newer app, and the older VaultSync would then have refused to run its sync engine over the newer one's, so nothing synced. The setup link now asks both apps which release they are before it changes anything. Where the installed one is newer, it leaves it in place, changes nothing, and says so with the command for that app's own setup, carrying the arguments you gave the link. An app that does not say which release it is, such as a development build, is not replaced either: the link says to move it to the Trash first. Another build of the same release, or an older release, is replaced as before. The change is live once merged, because the setup link serves the main branch. Recorded in decision 080.
- **A background service whose new Syncthing cannot be downloaded keeps syncing with the one it has** ([#267](https://github.com/psimaker/vaultsync/issues/267)) — when an update of VaultSync pins a newer Syncthing and its download fails (no network for a moment, or a checksum mismatch), the service ended at every start, every ten seconds, with nothing syncing until the download worked. It now keeps running the Syncthing it already has, where that is the very one VaultSync installed and recorded, unchanged since, not older than Syncthing 2.1.6, and with its configuration there; otherwise it ends as before. A download that makes no progress for 30 seconds ends then, and a slow one that goes on finishes. The service says so in its log, `vaultsync status` names the Syncthing installed and says what tries the new one again — `vaultsync stop`, then `vaultsync start`, where the service runs this VaultSync. Where `setup` runs from VaultSync for Mac, a failed download now says to run the app's own `setup` again, not a `vaultsync` command that may still lead to an older copy. Recorded in decision 078.
- **No sync engine is installed or started over data it may not belong to** ([#276](https://github.com/psimaker/vaultsync/issues/276)) — VaultSync's record (`agent.json`) can be lost while the engine's data stays, and a removal that stops midway can leave that data, or only the record, without the engine. `setup` and the background service took each of these for a fresh start: an older VaultSync could put an older Syncthing over a newer one's data, and an engine could start on half-removed data and bring back notes your other devices deleted. Now the background service changes nothing in any of these cases. `setup` takes the engine back only when no engine is recorded and the one there is the very one this VaultSync installs, and sets VaultSync up anew only where nothing of the engine is left. Otherwise it changes nothing. Both say how to go on: finish the removal, move the engine's folder aside, or set VaultSync up anew. This computer then pairs with your Hub again, and your vault files stay where they are. `vaultsync status` says the same. A missing engine program beside its data is no longer reinstalled by itself. Recorded in decision 077.
- **A `vaultsync uninstall --remove-data` that stops midway can be finished** ([#276](https://github.com/psimaker/vaultsync/issues/276)) — the removal now takes the sync engine's program and data first, and VaultSync's own copy and its record last. A removal stopped by a file it cannot remove says so and names the command that runs it again, which finishes it. Before, the record went first, and a second removal refused the folder as not VaultSync's own.
- **`vaultsync setup` no longer stops with "the sync engine did not start" when another program took the engine's port** ([#413](https://github.com/psimaker/vaultsync/issues/413)) — VaultSync's sync engine answers on a local port that `agent.json` records. Where the engine was not running and another program had taken that port, for example after the engine's folder was moved aside or while it was stopped, the engine moved to a free port when it started. `setup` still waited at the old one for a minute and then stopped. `setup` now picks a free port before it starts the engine, and records it. A running VaultSync keeps its port. Recorded in decision 079.
- **VaultSync waits for a sync engine an earlier run left behind, instead of starting a second one every ten seconds** ([#419](https://github.com/psimaker/vaultsync/issues/419)) — on a Mac, a `vaultsync run` in a terminal that is ended by a kill or a crash can leave its sync engine running for a while; the background service never does. A run started beside such an engine moved the engine's local port off it, started a second engine that stopped at once, and the background service then tried again every ten seconds, while `vaultsync status` called the engine not running. A run now leaves that engine and its port alone, starts no second engine, and starts its own on the same port once that one has ended. Meanwhile `vaultsync status` and the menu-bar icon say that an engine an earlier run left behind still holds the engine's folder and may still sync, and that VaultSync starts its own once it has ended; `pause`, `resume` and pairing say the engine is not ready yet and to try again shortly. Recorded in decision 086.
- **`vaultsync pair` says why it cannot reach the sync engine** ([#413](https://github.com/psimaker/vaultsync/issues/413)) — it used to say to start the engine. Where the background service runs but its sync engine does not, `pair` now says so and points to `vaultsync status`. Where VaultSync is still starting the engine, it says to try again in a moment. `pair`, `status`, `pause` and `resume` ask the engine only while VaultSync's own engine may run on this computer. Recorded in decision 079.
- **The setup link, run again to update, no longer asks for a pairing code** ([#380](https://github.com/psimaker/vaultsync/issues/380)) — on a computer that already synced with a Hub, an update through the setup link set up the new VaultSync and then searched for your Hub and asked for the code it printed. Without a terminal it stopped with "Pass the code your Hub printed". Now `setup` sees in the sync engine's own configuration that this computer syncs a vault with a Hub. It then says that VaultSync is set up and what it syncs, and ends. To sync another vault or pair with another Hub, run `vaultsync pair`. `setup` with a pairing flag (`--code`, `--hub`, `--vault`, `--create`, `--path`, `--yes`, `--name`) pairs as before, and a computer that syncs nothing yet is asked as before. Recorded in decision 081.
- **Ctrl-C ends a question in the terminal** ([#380](https://github.com/psimaker/vaultsync/issues/380)) — at a question of `vaultsync setup`, `pair` or `uninstall`, such as the one for the code your Hub printed, Ctrl-C showed `^C` and the question waited for Return. Ctrl-C now ends the question and the command at once. `setup` and `pair` say that nothing was paired, and `setup` what stays installed. `uninstall` says what it keeps, as for an answer of No.
- **`vaultsync start` no longer restarts VaultSync while it is coming up, and says it runs only once it answers** ([#290](https://github.com/psimaker/vaultsync/issues/290)) — on a Mac, `vaultsync start` and the menu's **Start VaultSync** stopped the background service and started it again even while it was still coming up, for example while it downloaded a new Syncthing, which then began again from the start. A service that runs and has begun its work is now left as it is; one that is stopping, waiting to be started again, or parked is started afresh as before, and so is one left alone that is gone by the end of the wait. On Linux, systemd already left a running service alone. On both systems `vaultsync start` used to say "VaultSync is running again" the moment the system counted the service as running, before VaultSync itself had come up. It now waits for VaultSync to answer, usually a moment and at most about twenty seconds, and only then says "running again", or "already running" for a service that was running before. Where it gets no answer, it says that the service does not answer yet, that `vaultsync status` says where it stands, and that `vaultsync stop`, then `vaultsync start`, ends it if it stays so. Where VaultSync recorded that it could not open its control socket, it says that instead. Recorded in decision 085.
- **From this release on, `vaultsync start` asks the background service which build it runs** ([#290](https://github.com/psimaker/vaultsync/issues/290), [#416](https://github.com/psimaker/vaultsync/issues/416)) — `start` judged whether the service runs its own build by comparing two files: itself, at the path it runs from, and the program the service names. A file can be replaced while the program started from it runs on. Run by its path, an older copy of VaultSync could find its file already replaced by a newer VaultSync for Mac's build, take the newer service for itself, and say that it does not sync, while it did. And a service that kept running after its program was replaced, for example VaultSync's own copy replaced by hand, was called "already running", as if it ran the new build. Every answer of VaultSync's control socket now says which build gives it, and `start` goes by that. Beside another build it says so, and that `vaultsync status` says whether it syncs; a service that runs is left as it is, as before. Where the service does not answer, `start` names no build, and what it says to do ends somewhere: `vaultsync status` says what the service does; `vaultsync stop`, then `vaultsync start`, where it stays so; and the setup link where that changes nothing, as beside a service of an older VaultSync, which does not sync and never answers. Where this `vaultsync` is older than the VaultSync set up on this computer, it says so, and that a service of its build does not sync, without claiming which build runs. Where the service of this very build answers while a newer VaultSync is set up, `start` says it runs, which it does until its next start, and names the setup link. The refusal of an older `pair`, `pause` or `resume` no longer says that nothing syncs, which it judged by the files too: it says that nothing syncs if the service runs that older build, until the setup link brings the current one. `vaultsync status` names `vaultsync stop`, then `vaultsync start`, as what installs a new Syncthing only where the running service says it is this build. A copy from an earlier release still judges by files; `vaultsync status` says whether the service syncs. Recorded in decision 093.
- **`vaultsync pair` writes nothing that comes from the Hub's address outside an answer** ([#323](https://github.com/psimaker/vaultsync/issues/323)) — bytes sent behind one of the Hub's answers stayed on the connection VaultSync kept for its next request: the HTTP library wrote them to the terminal as a line of its own (to the service's log when you pair from the menu), or read them as the next answer, and pairing failed. Bytes sent before the request could reach the terminal the same way. Each step of a pairing now opens a connection of its own, which is read only once its request is sent, and at most 64 KiB of an answer's head is read. Recorded in decision 062.
- **`vaultsync uninstall --remove-data` names a folder it may not look into as that, not as another disk** ([#278](https://github.com/psimaker/vaultsync/issues/278)) — where a folder in the sync engine's data could not be read, for lack of permission or for another reason, the removal stopped and said that the engine's folder held something from another disk, which sent you looking for a disk that is not there. It still stops there, as before, and now names that folder and says why: VaultSync may not look into it, and you can give your user access to it; or the system does not let VaultSync look into it, as macOS's privacy protection or a sandbox can; or VaultSync could not look into it, with the error. Only a disk mounted inside is called one. An entry that something else removed while the removal was at work no longer stops it.

## [0.3.0] — 2026-11-19

### Added

- **The menu-bar icon can start VaultSync when it is not running** ([#248](https://github.com/psimaker/vaultsync/issues/248)) — after `vaultsync stop`, or when the background service did not start, the menu offers **Start VaultSync**, which does what `vaultsync start` does and shows what that says, a refusal included. It runs the program the background service runs, never a `vaultsync` found on your `PATH`, so what it says is about that service. It does not appear when VaultSync was never set up here, or when the service has recorded that it could not open its socket; a service that is not installed says so when you click. A start that gets no answer from the service says so after about 15 seconds, and quitting the icon does not end a start under way.
- **Pair a Vault… works on Linux with KDE's `kdialog`, without `zenity`** ([#249](https://github.com/psimaker/vaultsync/issues/249)) — the menu asks for the code, the vault and the consent through whichever is installed, `zenity` first. In `kdialog`, the consent is a list with **Cancel** selected: Return alone never starts syncing.
- **When several Hubs answer, the menu offers them by name** ([#250](https://github.com/psimaker/vaultsync/issues/250)) — **Pair a Vault…** used to ask you to type your Hub's address under a list of what answered. It now shows a list, as the terminal does, and sends the code only to the Hub you choose. Return alone chooses none. A menu-bar app from 0.2.0 still running beside the new agent keeps asking for the address, and the new one does the same beside an older agent.

### Changed

- **Updated the Go runtime the desktop agent is built with** — Go 1.26.10 → 1.26.11 with the latest standard-library security fix; the [root changelog](../CHANGELOG.md) names it.
- **VaultSync installs Syncthing 2.1.7** — `setup` installs Syncthing 2.1.7 instead of 2.1.6, only if it matches the checksum built into VaultSync, as before; an update through the setup link moves an installed 2.1.6 to it. Once it is set up, a VaultSync from 0.2.0 — a VaultSync for Mac you kept elsewhere, or a downloaded `vaultsync` — no longer runs on this computer: it stops and says to run the setup link instead of putting 2.1.6 back (decision 054). 2.1.7 brings eight fixes from Syncthing, among them: data from another device that does not read right ends that connection with an error instead of stopping the engine, and a local change is checked before a shortcut for metadata-only changes is taken ([release notes](https://github.com/syncthing/syncthing/releases/tag/v2.1.7)).

### Fixed

- **On a Mac older than macOS 12 the setup link says that VaultSync for Mac needs macOS 12 or newer** ([#269](https://github.com/psimaker/vaultsync/issues/269)) — neither VaultSync for Mac nor the `vaultsync` agent runs before macOS 12, and on macOS 11 the setup link reported the download it had just checked as "The download does not hold VaultSync for Mac". **1) Obsidian device** now stops on such a Mac before it looks up or downloads anything, and says why. When the macOS version cannot be read, the setup goes on as before.
- **The terminal shows a Hub by its address first** ([#292](https://github.com/psimaker/vaultsync/issues/292)) — `vaultsync pair` named a Hub and then its address, in the list when several answer and in the line for the one it found. A name comes from whatever answers on the network: it can hold anything that looks like an address, and a name in Hebrew or Arabic letters drew the real address behind itself in a terminal that follows a text's direction. Both now start with the address, as the menu's list does. A Hub's name, this computer's name and the name you give a new vault also lose what can break a line or reverse the text after it: line separators, direction marks, control characters. What a name is written with stays: letters of any script, emoji, and the joiners some of them need. With `--create`, a name that is the name of a vault your Hub already has once it is cleaned counts as that vault's name and is not taken for a new one: a control character in it, or more than the 64 bytes that are kept of a name, used to send an empty folder that vault instead. Recorded in decision 061.
- **A Hub's error message is shown as one short line** ([#319](https://github.com/psimaker/vaultsync/issues/319)) — when pairing fails for a reason `vaultsync pair` has no words of its own for, it shows the message of the Hub's answer, in the terminal and in the menu's dialog. That message comes from whatever answers at the address, and it was shown as it came: with control characters, line breaks or a mark that reverses the text after it, and as long as an answer may be. It is now one line without those characters, cut to 300 bytes. The same holds for the reason a Hub gives when it could not share a vault or register this computer. A message a Hub words itself reads as before, a name in it with its spaces as written. The menu shows what the background service says, so it shows the short line once the service runs this version. Recorded in decision 062.
- **On Linux, names show as they are written in the pairing dialogs** ([#249](https://github.com/psimaker/vaultsync/issues/249)) — above an entry, a `&` read `&amp;`, a `_` went missing, and a backslash could break the line. The texts are now written for what each dialog does with them, tried on zenity 3.42, 3.44, 4.0 and 4.1. A long line is broken to fit: it could make a window wider than the screen, with its buttons out of reach.
- **Return alone chooses no vault in the Linux list** ([#249](https://github.com/psimaker/vaultsync/issues/249)) — zenity 4 opens the list with its first row selected, so Return took that vault. The list now starts with a row that chooses nothing and shows again if you continue on it; after the third time it says that nothing was chosen. Its rows show no number, and what you type finds only the words you see.

## [0.2.0] — 2026-11-05

### Added

- **On a Mac the setup link installs VaultSync for Mac, which runs the background service and opens the menu-bar icon at every login** ([#254](https://github.com/psimaker/vaultsync/issues/254)) — **1) Obsidian device** puts VaultSync for Mac into Applications (into `~/Applications` when your account cannot write there) and runs the setup from the app: the background service then runs from VaultSync for Mac, which macOS lists under Login Items, and the menu-bar icon opens when you log in — again by itself after a crash, not after you quit it. An existing service moves into the app once, which may make macOS ask once more for its permissions; the `vaultsync` command follows. An app of that name that is not VaultSync for Mac is never replaced, and with the app installed a `vaultsync` of another build (from this release on) stops and says to update the app instead of moving the service; and VaultSync's own copy does not sync beside an installed VaultSync for Mac at all — it stops within seconds of the app's arrival and stays so until the setup link (or the copy's own setup, without the app) sets it up anew; `vaultsync status` says so, and says it too when an older VaultSync left the service on its copy beside the app. Keep the app in Applications while VaultSync is set up — moved or put in the Trash, VaultSync stops syncing within seconds until the app is back where it was, and VaultSync's own copy (`~/Library/Application\ Support/VaultSync/bin/vaultsync status`) says so with the way back; `vaultsync uninstall` also quits the icon and removes its start at login (`--remove-data` no longer asks you to quit an icon VaultSync started), and points the `vaultsync` command back at that copy before the app goes to the Trash. `launchctl disable gui/$(id -u)/eu.vaultsync.tray` keeps only the icon from opening at login, and the setup leaves that so. An update never leaves you without a working app: the new one must run on your Mac before it takes the old one's place, and an update that stops halfway puts the old one back. A release without the app is set up with the bare agent, as before. Recorded in decision 053.
- **A menu-bar icon for VaultSync on a Mac or Linux computer** ([#176](https://github.com/psimaker/vaultsync/issues/176)) — `vaultsync-tray`, from the same release as the desktop agent, shows at a glance what `vaultsync status` says: a check mark when every vault is up to date, a ring while syncing, two bars while paused, an exclamation mark when a vault needs attention, a crossed ring when nothing syncs. The menu lists your Hub and each vault with the very words `status` prints (click a vault to open its folder), pauses and resumes syncing like `vaultsync pause` and `resume`, opens the service's log on a Mac, and pairs a vault through the desktop's own dialogs — the code, the choice of vault, and for a folder that already holds files the same consent the terminal asks for. It asks the running agent for everything over the socket the terminal uses and decides nothing itself; Quit closes the icon only, syncing goes on. On a Mac it comes as VaultSync for Mac (`VaultSync_darwin_<arch>.zip`, no Dock icon), which the setup link installs and opens at every login ([#254](https://github.com/psimaker/vaultsync/issues/254)); on Linux as `vaultsync-tray_linux_<arch>`, which you start yourself; on GNOME it names the extension that tray icons need, on Linux its dialogs need `zenity`; `vaultsync uninstall --remove-data` asks you to quit one you opened yourself first, before it removes the background service. Recorded in decisions 048 and 050.
- **Pause and resume syncing on a Mac or Linux computer without stopping the service** ([#176](https://github.com/psimaker/vaultsync/issues/176)) — `vaultsync pause` pauses every connection of the desktop agent to your Hub (nothing new arrives or leaves; the engine keeps running, your vaults and their settings stay as they are, and changes already received may still be applied for a moment) and `vaultsync resume` takes it back; `vaultsync status` says `paused on this computer` meanwhile and keeps showing what is still in progress. The running agent now answers status, pause, resume and pairing over a socket in VaultSync's folder, readable by your account alone — the one truth the menu-bar app shows.

### Changed

- **`vaultsync uninstall --remove-data` refuses before it removes the background service while VaultSync is in use, and says what stays** ([#176](https://github.com/psimaker/vaultsync/issues/176)) — with a menu-bar app you opened yourself running, or a `vaultsync run`, `pair` or `setup` in progress, it refuses before the service goes instead of removing it first and refusing after (on a Mac it may have removed the menu-bar icon's start at login by then, and says so); on a Mac it must be run from your own session, since it asks the service manager; it lists what it removed, names a folder it could not remove as an error (exit status 1), a folder that holds files VaultSync did not make as kept, and a folder that went meanwhile as gone. A `vaultsync run` that waited for VaultSync's folder while it was removed no longer sets VaultSync up afresh.
- **`vaultsync setup` and `pair` with `--create` no longer download a Hub vault of the same name** ([#176](https://github.com/psimaker/vaultsync/issues/176)) — `--create` asks for a new vault on your Hub; when your Hub already has one of that name, the agent now refuses and says to download that vault as the Hub's or to choose another name, instead of quietly downloading it into the folder (an empty folder would have received a vault you did not choose). A setup run again with the same flags still finds the vault it set up before and succeeds ([#228](https://github.com/psimaker/vaultsync/issues/228)).
- **VaultSync for Mac is signed with a Developer ID and notarized by Apple — a permission you give it stays given after an update** ([#222](https://github.com/psimaker/vaultsync/issues/222)) — the desktop agent `vaultsync` and VaultSync for Mac are signed with a Developer ID, run with the hardened runtime and are notarized by Apple (the app with its ticket stapled). macOS ties a permission such as access to Documents or the local network to that signature, so it now carries over to later releases instead of being asked for again after each update — once more when you move from an older, unsigned release, and possibly once when the background service moves into VaultSync for Mac ([#254](https://github.com/psimaker/vaultsync/issues/254)). A copy a web browser downloaded runs too; before, macOS blocked it. Recorded in decision 052.
- **The setup link sets up a Mac or Linux computer with VaultSync for Mac and Linux — no Syncthing to install first** ([#213](https://github.com/psimaker/vaultsync/issues/213)) — `curl -fsSL https://vaultsync.eu/setup.sh | sh` → **1) Obsidian device** downloads the desktop agent from its newest release (never a pre-release), checks it against that release's `SHA256SUMS` and runs its setup, which asks for the code and the vault; arguments after `--` go to the agent for scripts, and a dry run never prints the code, in whichever spelling it was passed. A Syncthing you already run is never touched; to pair that Syncthing itself with your Hub, use `vaultsync-hub pair` (see docs/hub.md). The link itself works again: it answered 404 until the landing page got its redirect ([#219](https://github.com/psimaker/vaultsync/issues/219)).
- **Updated the Go runtime the desktop agent is built with** — Go 1.26.6 → 1.26.10 with the latest standard-library security fixes; the [root changelog](../CHANGELOG.md) lists them.

### Fixed

- **An older VaultSync never puts an older sync engine back** ([#264](https://github.com/psimaker/vaultsync/issues/264)) — the desktop agent installs the Syncthing it was built with; a `vaultsync` older than the one set up on the computer (an old download, an older VaultSync for Mac dragged into Applications, a copy left behind) now stops and says to run the setup link, instead of installing its older Syncthing over the state the newer one wrote. Nothing is changed; the background service of such a build does not sync until the current VaultSync is back, and its `vaultsync status` says it is older; `vaultsync start` no longer judges a service that runs another build by its own version: it says so, and `vaultsync status` tells whether it syncs. desktop-v0.1.0, which knows nothing of this, no longer sets up or runs once this release's setup has taken over — use the setup link; until then a desktop-v0.1.0 that is still installed keeps running beside this release's `pair`, and a `run` it refuses changes nothing. Recorded in decision 054.
- **The menu-bar app says when macOS holds up opening a vault** ([#255](https://github.com/psimaker/vaultsync/issues/255)) — opening a vault in Documents, Desktop or Downloads from the menu makes macOS ask once whether VaultSync for Mac may open folders there; the menu waited half a minute for that answer, then showed nothing, and the folder did not open when you answered. It now says that macOS may be asking and to click the vault again once you have answered, and the note goes once the vault has opened. A vault folder whose name ends like an app (`Journal.app`) is shown in the Finder, never opened as an app — also when macOS does not let the menu look at it.
- **`vaultsync status` no longer calls the background service stopped when you are simply not logged in yet** ([#232](https://github.com/psimaker/vaultsync/issues/232)) — on a Mac reached over SSH before anyone logged in at the screen (and on Linux when your systemd user manager is not running — your last session ended without `loginctl enable-linger`), the service has no session to run in: `status` and `start` now say that it waits for your login, instead of sending you to `vaultsync start` or printing the service manager's error.
- **Running the desktop agent's setup again with the same flags no longer refuses with a folder that “overlaps itself”** ([#228](https://github.com/psimaker/vaultsync/issues/228)) — a script that runs `vaultsync setup --vault X --path P` a second time now hears that X is already set up to sync at P and succeeds, with no second share request to the Hub and no change on this computer; naming another folder for a vault that is already set up here says where it is instead. Every other overlap is refused as before.

## [0.1.0] — 2026-10-06

### Added

- **VaultSync for Mac and Linux: a desktop agent that brings its own Syncthing** ([#175](https://github.com/psimaker/vaultsync/issues/175)) — one program, `vaultsync`, turns a computer without Syncthing into a VaultSync device: `vaultsync setup` downloads Syncthing 2.1.6 and installs it only when it matches the checksum built into VaultSync, runs it in the background with its own settings (a LaunchAgent on macOS, a systemd user service on Linux; no administrator rights), pairs with your Hub by code — asking which Hub printed it when several answer, and sending the code only there — and offers your Obsidian vaults (newest first, from Obsidian's own list) next to the vaults on your Hub. A Hub vault arrives in a new, empty folder; a vault from this computer becomes a new vault on your Hub, and a folder that already holds files syncs only after you agree to sync that very folder, and only with a vault your Hub reports as new, empty and shared with this computer alone — the agent checks everything again, here and on the Hub, right before it connects the folder. Vaults inside iCloud Drive, OneDrive, Dropbox, Google Drive or Nextcloud are refused, because their placeholder files would sync as deletions. A Syncthing you already run is never touched; folders it syncs are never synced twice. `vaultsync status`, `pair`, `stop`/`start` and `uninstall` (your vaults always stay) complete it; Windows follows. Documented in `docs/hub.md`; recorded in decision 046. Shipped as `desktop-v*` releases (the first: `desktop-v0.1.0`).
